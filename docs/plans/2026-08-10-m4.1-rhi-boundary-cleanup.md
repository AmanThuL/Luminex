# M4.1 — RHI Boundary Cleanup

**Status**: In progress

## Outcome

Luminex enters M5 with an extraction-ready RHI component boundary, explicit domain-owned failure
types, self-contained includes, and enforceable source/API documentation conventions. This work
does not add rendering features or pre-empt M5.1's caller-facing interface experiment.

## Decisions

- Keep errors owned by the domain that can explain them. RHI, Engine assets, Render Graph, and App
  options retain distinct result aliases and error values; no global `lmx::Error` is introduced.
- Move RHI to a repository-root component with a public include tree, private implementation tree,
  backend tree, and its own xmake definition. Preserve namespaces and caller-facing signatures.
- Keep public headers self-contained. Do not introduce a shared umbrella header; use a target-private
  precompiled header only if repeatable clean-build measurements justify it.
- Use 120-character hyphen rulers for file-header envelopes and the existing 120-character equals
  rulers for implementation function/test boundaries.
- Document public and protected header APIs with Doxygen. Private implementation comments remain
  sparse and explain only non-obvious contracts or rationale.

## Work

1. Add file-header and API-comment conventions, update the Clang-backed layout checks, and cover all
   project-owned C++ sources with a uniform file header.
2. Move the RHI public surface, validation, capture schema, and Metal 4 backend into `RHI/`; load its
   target definition from the root build and update every path-aware tool and document.
3. Separate Metal 4 ImGui integration from the core RHI target while keeping the existing App path.
4. Extract RHI error/result declarations into a self-contained public header without changing
   signatures. Preserve explicit error translation at Engine/App boundaries.
5. Remove accidental transitive includes, prove public headers compile independently, and record
   clean-build measurements before deciding whether a private PCH is warranted.
6. Convert existing public contracts to Doxygen in RHI, Core, Render, Engine, and App; add structural
   and compiler-backed checks without requiring a Doxygen installation.
7. Refresh the roadmap, architecture, frame walkthrough, operations, and milestone record, then
   remove this executor plan once the maintained baseline contains its durable results.

## Non-goals

- Compute, storage resources, general barriers, subresource views, graph pooling, or other M5 work.
- A new caller-facing RHI model, a second backend, or the M5.1 interface experiment.
- Eliminating every host diagnostic/tooling dependency required to publish RHI as a separate repo.
- Moving the root test suite into the RHI component.

## Validation

- `xmake format --check`
- `xmake policy`
- Public-header standalone compile checks
- `xmake`
- `xmake test Tests/unit`
- `xmake test`
- `MTL_DEBUG_LAYER=1 xmake test Tests/gpu`
- Offscreen Sponza, Damaged Helmet, and MaterialLab smoke renders

## Exit gate

The RHI builds from its root component without exporting backend implementation paths or requiring
ImGui in the core target; existing callers retain their API and failure semantics; every owned C++
file has a valid file header; public API documentation and include self-containment are checked by
policy; all CPU/GPU validation remains green; and current architecture documents name the new
boundary without presenting it as an independently published library.
