# M5.1 — RHI Execution-Model Decision

**Status**: In progress

This plan executes the accepted design in
`docs/specs/2026-08-12-m5.1-rhi-execution-model-design.md`. `docs/roadmap.md` owns the M5.1
outcome, deliverables, exit gate, and deferrals; this plan decomposes that boundary without
expanding it. The spec froze the scored workloads, measurement protocol, rubric, and adoption
thresholds before any measurement; stages below reference those frozen definitions and may not
change them. Exploratory additions must be marked unscored and cannot influence the ADR.

## Outcome

A measured prototype decides whether to retain, partially reshape, or replace the object-shaped
RHI with a smaller GPU-address-first interface honest to Metal 4 and D3D12. The experiment ends in
an ADR selecting one production direction; the prototype is retained as a frozen non-normative
research artifact per the spec's fixed disposal policy. Production runtime sources and public
contracts are not modified; checkpoint A stays green throughout.

## Integration

All work accumulates on the outcome branch `spike/m5.1-execution-model` (the existing milestone
branch renamed to satisfy `docs/conventions/commits.md`), which reaches protected `main` in a
single pull request. The spec, this plan, and the `AGENTS.md` active-plan pointer are committed on
this branch when the milestone starts; nothing lands on `main` directly. Every stage passes
`xmake format --check`, `xmake policy`, and the untouched production suites before it is
considered done; experiment GPU coverage runs under `MTL_DEBUG_LAYER=1` on Metal 4 Apple Silicon,
while scored performance runs keep validation off per the spec's protocol. Build manifests may
gain the non-default experiment targets; that is the only production-tree change.

## Stage 1 — Model synthesis, manifest, and mapping draft

1. Synthesize the comparison model from the three sources the roadmap names into a short internal
   model summary: for each of the six areas — memory/address and root data, handles and bindings,
   pipelines and commands, attachments and synchronization, residency and capabilities, debugging
   and failure behavior — what the model prescribes and what it deliberately omits.
2. Define the prototype interface under `Experiments/NoApi/` (namespace `lmx::noapi`) covering
   exactly those six areas at the spec's scope.
3. Add the non-default xmake targets with the spec's frozen dependency boundaries: `NoApiProto`
   (metal-cpp and `Source/Core` only, no `RHI/` includes), `NoApiTests` (prototype only),
   `NoApiBench` (the comparison host, linking both the production RHI and `NoApiProto` through
   two adapters), and the API-neutral workload manifest library (no `RHI/` or `NoApiProto`
   includes). A plain `xmake` builds none of them.
4. Implement the workload manifest for the spec's scored core: the thirteen-pass representative
   graph with its resource table, the frozen draw/material/update algorithms and synthetic asset
   generation, the hazard case table H01–H24 with exact resources, ranges, and expected values,
   the S-BIND, S-LIFE, I1–I4, and M1–M6 definitions, and the resolved values of every *prod*
   reference. Add the consistency test that declares the representative graph to the production
   `RenderGraph` and asserts the manifest's schedule and barrier expectations against the
   compiled record.
5. Start the evidence document as a working draft carrying the mapping classification table:
   every interface concept × {Metal 4, D3D12} → native/emulated/unavailable/unknown, with
   shader-constraint findings recorded alongside and Vulkan as an unscored comparative column.

Exit: the interface header and manifest library compile in non-default targets; the consistency
test passes against the production graph; the classification draft covers all six areas for both
scored APIs; production runtime sources are untouched.

## Stage 2 — Prototype core

1. Implement the interface on Metal 4 with metal-cpp: allocator and address model, root data,
   bindless table, pipeline creation, flat command recording with pass-boundary attachments,
   barriers and fences honoring the three-frames-in-flight rules, residency set, deterministic
   creation-failure reporting.
2. Give every GPU object a label and every misuse path an assert with context, matching the
   spec's debugging and failure gates.
3. Add `NoApiTests` smoke coverage: an offscreen render and readback exercising each area of the
   interface at triangle scale, run under `MTL_DEBUG_LAYER=1`.
4. Record every place the implementation had to emulate, bound, or deviate from the synthesized
   model as findings in the evidence draft, including Slang → MSL binding constraints and any
   hand-written MSL frontend the spec's shader-control rule permits.

Exit: smoke coverage passes under Metal validation with no warnings; the frozen `[checkpoint-a]`
filter still passes unchanged; the evidence draft's Metal 4 column reflects what was built.

## Stage 3 — Adapters, parity, and the representative graph

1. Implement the maintained-RHI adapter in `NoApiBench`, executing the manifest with production
   shaders and pipelines unchanged, and its per-frame work documented against the spec's timed
   region.
2. Implement the prototype adapter over the same manifest with the experimental binding frontend
   around the shared math modules; document its per-frame work the same way.
3. Implement the readback parity oracle and run the frozen 32-frame correctness run, asserting
   byte-identical output on every frame, including the persistent exposure buffer's cross-frame
   feedback edge under three frames in flight.

Exit: both adapters produce byte-identical output for all 32 frames under Metal validation; the
timed-region documentation for both adapters is reviewed against the spec.

## Stage 4 — Stress cases and scored collection

1. Implement H01–H24 as positive correctness cases on both adapters, asserting the manifest's
   expected values.
2. Implement S-BIND at both frozen scales, S-LIFE's 12-frame schedule with its mid-flight upload,
   and I1–I4, all readback- or assertion-verified on both adapters.
3. Implement M1–M6 as subprocess death-tests capturing assert category and message on both sides.
4. Build the measurement instrumentation the spec's rubric names: the timed encode region, binding
   call and byte counters (root structs, table entries, handle arrays, amortized population),
   barrier counts, allocation counters including prototype table/metadata/heap overhead, and the
   API-surface counting under the spec's shared rules.
5. Collect all scored measurements under the frozen protocol — paired AB/BA repetitions, 12 pairs,
   16 warm-up plus 256 measured frames, bootstrap confidence intervals for time metrics, exact
   counts for count metrics, validation off for performance runs — plus the capture-quality
   checklist on Xcode GPU captures of both adapters, and record everything in the evidence draft
   with environment details. The spec's measurement freeze gate applies from the first scored run.

Exit: every scored case passes on both adapters; every rubric dimension has recorded values with
uncertainty or exact counts; misuse behavior is captured on both sides; no scored data predates
the last interface/workload/shader/instrumentation change.

## Stage 5 — Judgment and record

1. Apply the spec's frozen gates, then its symmetric material win/regression thresholds and
   change-proportional rules, to the recorded evidence; for a replace outcome, produce the
   checkpoint A coverage matrix the spec requires. Finalize the evidence document under
   `docs/research/` as frozen and non-normative.
2. Record the decision as an ADR in `docs/decisions/` selecting retain, partial reshape, or
   replace, stating the evidence against each frozen threshold, recording the experiment's frozen
   non-normative status and last verified environment, and, if production change is adopted,
   naming the separately accepted M5.x migration completed before M6 with no parallel API left.
   This milestone migrates nothing.
3. Re-run the frozen `[checkpoint-a]` filter and the full production suites at the milestone tip.
4. Write `docs/milestones/m5.1.md` with shipped evidence and limits; update the roadmap's
   current-baseline section; refresh `AGENTS.md` where commands or the active-plan pointer
   changed; close this plan per `docs/conventions/documentation.md`.

Exit: the roadmap's M5.1 exit gate holds with recorded evidence; documentation checks pass; the
milestone record truthfully reflects the gate evidence.

## Non-goals

Per the roadmap's M5.1 deferrals: a production D3D12 backend, Vulkan/Linux support, multi-queue
optimization, ray tracing, production interface migration, and later rendering features.
Additionally out of scope: any modification to production runtime sources or public contracts,
porting `SceneLibrary`/assets/UI/swapchain into the experiment, and any scored workload beyond
the spec's frozen definitions.

## Validation

- `xmake format --check` and `xmake policy`
- `xmake test` (production suites, untouched throughout)
- The frozen `[checkpoint-a]` filter at milestone start, after stage 2, and at the tip
- `MTL_DEBUG_LAYER=1` runs of `NoApiTests` and both `NoApiBench` adapters for correctness;
  validation off for scored performance runs per the spec
- Byte-identical parity oracles for the representative graph and every scored case claiming
  output
- The spec's frozen measurement protocol for every rubric dimension

## Exit gate

The roadmap's M5.1 exit gate applies verbatim: checkpoint A stays green; the prototype reproduces
the output, failure behavior, and three-frame lifetime rules it claims to cover; all emulation,
fallback, shader constraints, gaps, and risks are recorded; evidence is judged against the frozen
thresholds; an ADR selects one production direction and disposes of the experiment.
