# Neural and learned rendering techniques, 2022–2026

**Status**: Frozen — non-normative  
**Research date:** 2026-09-14

Evidence notebook for the [rendering direction review](../2026-09-14-rendering-direction-review.md),
collected in one web-assisted pass over papers, SDKs and vendor research pages. It supplies the
literature under the ideas assessed in the
[2026-09-06 project-fit assessment](../2026-09-06-graphics-paradigm-project-fit.md) rather than
re-pitching them. The review reconciles conflicts between notebooks and takes precedence over any
judgment here. Items marked **[UNVERIFIED]** were not confirmed against a primary source; recheck
them before a plan depends on them.

**Cross-cutting finding that changes the runtime-feasibility calculus below:** Metal 4 (macOS 26,
Luminex's actual target) ships a first-party in-shader ML inference substrate functionally
equivalent to DirectX Cooperative Vectors — `MTLTensor`, `MTL4MachineLearningCommandEncoder`, and
"Shader ML" (`tensor_ops::matmul2d` from `MetalPerformancePrimitives`, callable directly from a
fragment/compute function, synchronized via `MTLStageMachineLearning` barriers). Apple's WWDC 2025
session 262 ("Combine Metal 4 machine learning and graphics") explicitly demos in-shader CNN
ambient-occlusion inference, neural texture decompression, and ML upscaling as worked examples. So
"no runtime CUDA" does **not** mean "no in-shader MLP inference" for Luminex — small trained
networks can run as ordinary compute/fragment passes in the existing render graph, trained offline
on rented NVIDIA GPUs exactly as the owner intends, with weights imported via `metal-package-builder`
(PyTorch/TensorFlow → CoreML → `.mtlpackage`). (Source: developer.apple.com/videos/play/wwdc2025/262/
and /205/, observed 2026-09-14.)

## 7. Generative / world-model landscape (assessed, largely non-transferable)

**Honest paradigm assessment:** diffusion/transformer world models are **not a component a rasterization/RHI renderer like Luminex can adopt** — they wholesale replace the renderer, the engine, and the simulation logic with a frame-autoregressive generative video model that never touches a mesh, BVH, or shader. None expose geometry, materials, or a scene graph. Several 2024-era entrants have already been repositioned by their own creators toward **robotics/autonomous-vehicle/physical-AI simulation** rather than gameplay/rendering. This is a disjoint paradigm, not an extension of a traditional GPU renderer.

## Techniques a Metal-first solo renderer could realistically ship as experiments, ranked

Ranked by (a) reuse of Luminex's existing PBR/temporal/IBL contracts, (b) availability of an open training recipe, (c) measurability against an analytic/reference oracle, (d) independence from vendor-specific hardware.

1. **Neural Irradiance Volume (inference-only MLP GI probe)** — "done" = an offline bake tool (à la `Tools/TextureBake`) trains a tiny hash-encoded MLP per scene against path-traced ground truth; runtime is a Metal 4 Shader-ML compute pass sampled from the G-buffer, replacing/augmenting IBL with directional indirect light; measured against a reference path-traced bake.
2. **Hybrid analytic-microfacet + neural residual BRDF** — "done" = a small residual MLP grafted onto the existing GGX pipeline for one hero material, trained offline against a reference (Mitsuba 3), A/B'd against pure-GGX at matched frame cost.
3. **OIDN-style / ExtraNet-style neural denoiser or extrapolator as a post-pass** — "done" = OIDN or a from-scratch ExtraNet-shaped network (open code, G-buffer/motion-vector-compatible) running as a Metal compute pass alongside/after `TemporalResolve`, benchmarked against native TAA on the existing temporal-comparison tooling.
4. **STSSNet/FuseSR-style joint spatial-supersampling+extrapolation pass** — "done" = an open-recipe network trained offline, evaluated against Luminex's own TAAU at matched render scale, using existing FLIP-based comparison tooling.
5. **Neural texture compression as a BC/ASTC alternative (NTC-inspired, Metal Shader-ML decode)** — "done" = a small per-material-set decoder MLP trained offline, decoding textures in a Metal 4 compute pass at competitive cost to the existing DDS/BC1 baseline, on Sponza/Damaged Helmet assets already in the repo.
6. **KiloNeuS-style real-time neural SDF for a single hero asset** — "done" = one asset (e.g. Damaged Helmet) represented as a small partitioned-MLP SDF, sphere-traced in a compute pass, compared against the existing mesh rasterization path for quality/cost.
7. **Neural Bounding for render-graph culling** — "done" = a trained (or even "non-deep" second-scale) tighter-bounds classifier feeding Luminex's existing culling/LOD-selection logic, measured by culling accuracy vs. AABB baseline.
8. **Neural shadow post-filter (kernel-predicting network on existing shadow maps)** — "done" = a small MLP filter kernel applied as a post-pass on Luminex's current shadow-map output, compared against PCF/PCSS baselines for softness/quality at equal cost.
9. **Slang-autodiff-based offline material/lighting fitting tool** — "done" = a Slang `[Differentiable]` shader pipeline that gradient-fits a procedural material or light-probe parameter set against reference images, feeding Luminex's existing scene/material system — pure tooling upside, near-zero runtime risk.
10. **SPZ-style splat compression bake step (feeding the already-scoped hybrid mesh/splat runtime)** — "done" = an offline SPZ-format compression pass over captured/trained splats, validated for round-trip fidelity, directly useful infrastructure for the splat-conformance lab already on the roadmap.

Items 1, 3, 4, and 9 rank highest overall: each reuses an existing Luminex contract (IBL/G-buffer, `TemporalResolve`, TAAU, or the Slang toolchain respectively), has an open or reproducible training recipe, and can be measured against a reference Luminex already has tooling for (path-traced bake, FLIP comparison, or reference-image fitting). Items depending on RT hardware (N-BVH, LSNIF, neural intersection functions) are excluded from this top-10 — they are real, well-documented techniques but structurally gated on an RT pipeline Luminex does not have.

## Techniques that are hype or not renderer-shaped

**Generative world models (GameNGen, Oasis, Genie/Project Genie, Muse/WHAM, DIAMOND, Cosmos 3, and 2026 entrants like Waymo's model and Alibaba's Happy Oyster)** are the clearest case: they replace the entire engine and renderer with an autoregressive video-generation model that never constructs a mesh, BVH, or shader — there is no "adopt this technique in an RHI" path, only "replace the RHI." Several vendors have already pivoted their own flagship products away from gaming toward robotics/AV/physical-AI simulation, which is independent corroboration this is a separate industry track, not a renderer feature pipeline. **RTX Mega Geometry**, despite NVIDIA's "neural rendering" branding, is not actually neural — it's classical GPU-accelerated triangle clustering/BVH-build acceleration, and should not be conflated with genuine learned-BVH work (N-BVH) when scoping a roadmap. **"Neural Assets" as a term** (Google DeepMind, NeurIPS 2024) is 2D pose-controllable image-diffusion scene synthesis, not a 3D asset-compression format — a naming false-friend worth flagging so the roadmap doesn't chase the wrong paper. Most **neural frame-generation SDKs (DLSS FG, FSR FG, DLSS Ray Reconstruction)** are legitimately shipping and useful for users, but have zero published training method — they are integration targets, not experimental-feature literature, and cannot be reproduced on rented GPUs.

## Training/hardware notes

The smallest credible training setups by technique class: **per-material/per-texture-set MLPs (NTC-style compression, neural BRDF/appearance, material distiller)** — a single rented A6000/4090-class GPU, hours to a day per material/scene, PyTorch + a custom fast trainer if following NVIDIA's approach (their own paper notes a general framework like PyTorch is ~10× slower than a hand-rolled trainer for this workload). **Per-scene inference-only GI networks (Neural Irradiance Volume, Neural Light Grid)** — one rented GPU, tens of minutes to hours per scene, needs a path-traced ground-truth generator first (Mitsuba 3 or a custom offline path tracer) to supply training targets. **Denoising/upscaling/extrapolation networks (OIDN-style, ExtraNet, STSSNet, FuseSR)** — heavier: needs a corpus of many rendered frames with G-buffer/motion-vector ground truth across varied scenes/camera paths, best generated by instrumenting Luminex's own capture-sequence tooling; single high-VRAM GPU (24GB+) for days is plausible given the published dataset scales. **Online-trained caches (NRC-style)** — no offline training needed at all; the cost is architectural (implementing online gradient updates inside the render loop), not GPU-hours. **Differentiable-rendering/Slang-autodiff tooling** — no training in the ML sense; compile-time only, runs on the dev machine.
