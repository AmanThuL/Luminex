## 2. On-GPU ML on Apple Silicon: what is actually usable from a renderer in 2026-09

There are **two distinct, non-interchangeable** Metal 4 paths to "ML in a renderer," and Luminex
would use hand-written MSL for either, not Slang:

**Path A — Core ML inference as a GPU-timeline pass.** Train/export a model with Core ML tools
(or MLX → Core ML), convert it at build time with `metal-package-builder` (bundled in Xcode 26)
into a Metal ML package, load it into an `MTL4MachineLearningPipelineState`, and dispatch it from
an `MTL4MachineLearningCommandEncoder` alongside render/compute passes in the same command buffer,
synchronized via `MTLStages.machineLearning` and ordinary Metal 4 barriers. Apple's own doc is
explicit that "machine learning encoders run Core ML models but they can't build new networks or
modify layers" — this is an *inference-only* black box from the GPU-timeline side; the network
architecture is fixed at model-conversion time. The system, not the app, chooses GPU vs. Apple
Neural Engine per model, so a shader-adjacent app cannot force ANE execution. This is the path for
"drop a pretrained small tonemap/denoise network into the frame," matching WWDC26 session 359's
neural-tonemapper example.

**Path B — MSL-native tensor ops inside a shader ("inline ML").** Metal Shading Language 4 adds
`tensor_handle` (CPU-created `MTLTensor` wrapped for GPU use), `tensor_inline` (a GPU-side view
over a buffer, no host round-trip), and `cooperative_tensor` (values distributed across a
thread's registers/threadgroup memory, never spilled to device memory — the mechanism for
latency-critical inline ops). Metal Performance Primitives supplies `matmul2d` and friends as the
actual math kernels; a tiny MLP is expressed as a sequence of `matmul2d` + activation calls inside
an ordinary compute (or, per Apple's doc, *any* shader stage including vertex/fragment) kernel,
issued collectively at simdgroup/threadgroup scope. This is genuinely usable today — an
independent working example exists (`liuliu/example_matmul_metal4`) — but the author explicitly
flags that both the reference header (`MPPTensorOpsMatMul2d.h`) and the MSL 4 specification's own
example code contain stale/incorrect API usage, requiring a workaround
(`dynamic_length_v<int>`). Treat this surface as early and under-documented, not turnkey.

**Precision/shape constraints:** `MTLTensor` supports common weight/activation types (`int8`,
`fp16` confirmed in Apple's own text); accumulation in `matmul2d` happens at ≥fp32 per the Rigel
reverse-engineering paper. Quantized 4-bit formats and fp8 block-scaled formats are claimed by a
secondary source for "macOS/iOS 27" — **not yet current** as of 2026-09-14 (macOS 26 is current)
and unverified against an Apple primary page.

**Slang emission: no.** Slang's own Metal-target documentation lists supported/unsupported
features and contains no mention of `tensor_handle`/`tensor_inline`/`cooperative_tensor` or
`matmul2d`; separately, Slang's cooperative-vector feature (the closest conceptual analog) is
explicitly scoped to the SPIR-V/NVIDIA vendor-extension path only, not Metal. The shader-slang
org's own SIGGRAPH-2026 neural-shading course materials confirm this split: the coop-vector
examples require Windows/Linux + NVIDIA, and only non-tensor examples (mipmap, "network"/SlangPy
host-side, UTracer) run on macOS/Metal. **Consequence for Luminex: any Metal 4 tensor-ops
experiment must be authored as raw `.metal`/MSL and integrated as a hand-written shader module
alongside the Slang-compiled pipeline — it cannot go through the existing Slang→Metal path.**

**Performance vs. plain FP16 ALU code — what's actually measured:** The one independent
microbenchmark found (Rigel, arXiv:2606.12765, submitted 2026-06-11, reverse-engineering M4 Max)
found `matmul2d` "executes entirely on the GPU shader cores with no dedicated matrix datapath and
no evidence of ANE routing" on **M4** — i.e., on Luminex's current M4-class hardware, the MSL
tensor-ops path is not accelerated beyond what hand-written FP16 ALU code would achieve; fp8 on M4
is "emulated, not accelerated" (0.94x fp16 throughput despite half the bytes). This is the single
most important unknown for the roadmap: **the Neural Accelerator payoff is an M5/A19-Pro-class
hardware fact, not a Metal-4-software fact** — the same MSL code on M4 gets no matrix-unit
speedup. A separate LLM-inference paper (BaseRT, arXiv:2607.19438, July 2026) measured large
speedups from hand-fused Metal 4 tensor kernels specifically on **M5 Pro** hardware (up to 6.4x
vs. llama.cpp, 3.9x vs MLX on prompt processing) — consistent with the Neural Accelerator being
the source of the gain, though that paper targets LLM GEMM/attention kernels, not a real-time
renderer's per-frame tiny-MLP workload, so its numbers are suggestive, not directly transferable.

**Unknowns to flag explicitly:** (1) No official Apple number for "tiny MLP in fragment shader"
per-frame cost on any chip. (2) No confirmation of the exact `.apple10`/`.apple11` `MTLGPUFamily`
→ chip mapping in Apple's own docs (only inferred from secondary sources). (3) Whether
`cooperative_tensor` register pressure at fragment-shader (not just compute) granularity is
practical — Apple's doc says "any GPU stage" is legal but gives no fragment-shader-specific
guidance or perf data. (4) Whether Metal 4's ML-encoder inference-only restriction (Path A) could
be circumvented for a truly custom architecture other than by staying on Path B (MSL tensor ops).

## 3. Apple hardware purchase implications

Yes — a newer chip is not a cosmetic upgrade here, it is a functional gate. On the recorded
development machine, the Metal 4 tensor-ops API (`matmul2d`/`cooperative_tensor`) **compiles and
runs but is not accelerated**: per the Rigel reverse-engineering paper, it executes on ordinary
GPU shader cores with no dedicated matrix datapath, so an in-shader MLP experiment on M4 would be
measuring "MSL tensor-op call overhead vs. hand-written ALU code," not "Neural-Accelerator
speedup." An **M5 or A19-Pro-class chip** is required to exercise the actual per-GPU-core Neural
Accelerator that WWDC26's neural-rendering sessions are built around, and that Apple's own M5
newsroom text says is reachable specifically via "Tensor APIs in Metal 4." Within the M5 family,
plain M5 (10-core GPU) is sufficient to validate the programming model and see the hardware path
engage; M5 Pro/Max only add GPU core count / bandwidth, not new capability classes, for this
purpose (that Pro/Max launch claim itself is from a secondary/tertiary source and should be
reconfirmed against apple.com before a purchase). Given Luminex's stated interest (tone-mapping,
denoising, tiny in-shader MLPs), a base M5 machine appears to be the minimum bar that unlocks the
experiment class the owner is asking about; it is not clear any Mac purchase is *required* before
prototyping starts, since Path A (Core ML inference passes) and Path B (MSL tensor ops, measuring
overhead only) both compile and run on existing M4 hardware — only the "does the Neural
Accelerator actually help" measurement requires M5.
