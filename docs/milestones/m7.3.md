# M7.3 — GPU Visibility and Work Generation

**Status**: Implemented — owner review pending

This design specification preceded implementation. The [validation record](m7.3-validation.md)
owns implemented behavior, measured results and remaining failed gates. The
[roadmap](../roadmap/gpu-driven-hybrid-rendering.md#m73--gpu-visibility-and-work-generation)
owns the outcome, deliverables, exit gate and deferrals; [ADR 0021](../decisions/0021-gpu-scene-handoff-contract.md)
owns the identity, update and graph-participation semantics the GPU writer must keep; and
[ADR 0012](../decisions/0012-gpu-submission-defer.md) owns the M5.6 closure and the adoption bar
this slice measures against without reopening. Where wording differs, those win. The owner
authorized execution on 2026-09-15; implementation is complete and manual review remains pending.

## Objective and baseline

GPU frustum visibility and work generation have a validated production path measured against the
M7.2 reference. The baseline is [M7.2](m7.2.md) with its [validation record](m7.2-validation.md):
`Visibility.h` classifies every candidate on the CPU against five guarded planes of the jittered
view-projection, `DrawSubmission` writes a visible-row list and 20-byte indirect arguments into
three paced slot buffers, and `ShadowStage`/`SceneStage` issue one CPU command per visible entry
(direct, indirect) or per pipeline/material/mesh run (batched) through the shared
`gVisibleRows[gDraw.firstEntry + instanceIndex]` contract. Both draw buffers are CPU-written
graph imports without GPU writers. Metal has no multi-draw indirect without indirect command
buffers, so a GPU-decided draw still needs a CPU-issued command per slot.

This slice moves classification and the production of rows and arguments to the GPU and keeps
everything they mean: scene-linear materials, pre-exposure, masked coverage (ADR 0018), the motion
convention (ADRs 0013–0017), the display boundary (ADR 0019), the M7.1 identity rules and the
M7.2 row ABIs, slots and shader contract are unchanged. The CPU oracle remains the maintained
reference and the default. The GPU path fills fixed argument slots, so the CPU command count stops
depending on visibility and that remaining encoding is measured and disclosed. A bounded spike
decides whether a capability-selected indirect command buffer (ICB) adapter joins the slice; the
roadmap's "ICB remains optional" stays true either way.

## Intended implementation

### Modes and candidate order

`render::ClassifyMode { Cpu, Gpu }` joins `SubmissionMode` in `Visibility.h`; `SceneView`
carries it beside `visibilityEnabled` and `submission`. `--classify <cpu|gpu>` (default `cpu`)
applies to every run mode. GPU classification requires `indirect` or `batched`; `direct` is
rejected because it binds a per-draw selector the CPU must already know. `--visibility off` under
`gpu` still runs the kernels with culling disabled, so every candidate bypasses with reason
`Disabled` as on the CPU. Defaults stay CPU classification with indirect submission.

The CPU keeps owning candidate order. `buildDrawSubmission` gains a candidate table and run
descriptors in the canonical order of the submission mode: object order for indirect, where every
candidate is its own run, and the M7.2 stable sort by alpha mode, double-sided flag, material row
and mesh row for batched. `DrawSubmission::prepare` uploads them into new paced slot buffers,
rewritten only when their bytes change. Because the CPU still knows every run's mesh, textures
and pipeline, it encodes the fixed command stream: one command per candidate slot in the sparse
layout, one per run in the dense layout, regardless of what the GPU retains.

| Record | Fields (byte offset) | Size |
|---|---|---|
| `CandidateRecord` | instanceRow (0), run (4) | 8 |
| `RunRecord` | firstCandidate (0), candidateCount (4), firstSlot (8), argumentIndex (12) | 16 |
| `ChunkRecord` | run (0), firstCandidate (4), candidateCount (8), padding (12) | 16 |
| `VisibilityViewParams` | planes as 5 × float4 (0), flags (80), firstCandidate (84), candidateCount (88), firstRun (92), runCount (96), firstChunk (100), chunkCount (104), padding (108) | 112 |
| `VisibilityParams` | layout (0), rowCapacity (4), argumentCapacity (8), stateCapacity (12), candidateCount (16), viewCount (20), padding (24) | 32 |

`Source/Render/VisibilityTables.h` and `Shaders/Modules/Visibility.slang` mirror these with
size and offset asserts; the module also owns the state encoding, `state | reason << 2` with the
numeric values of `VisibilityState` and `VisibilityReason`, and the shared p-vertex function.

### Views and kernels

A view is a plane set plus a candidate range and an output range. M7.3 declares scene and shadow
views; the shadow view sets the unculled flag and goes through the same kernels, so counts stay
comparable and M8.1 can add cascade views without a new mechanism. Planes come from the existing
`extractFrustumPlanes` on the same matrix the CPU oracle uses; only the box test moves to the GPU.

`Source/Render/GpuVisibility.h` owns the pipelines, the per-slot state and counter buffers and
four passes grouped under `lmx.pass.visibility`:

- `lmx.pass.visibility.reset`: a copy pass fills the counters to zero.
- `lmx.pass.visibility.classify`: one thread per candidate reads its instance row's world box
  and flags, applies the CPU bypass precedence (disabled, unculled view, nonfinite transform,
  unreliable bounds) and the p-vertex test, writes the state word to `lmx.draw.states`, and
  writes each chunk's retained count to a one-frame transient. A chunk is
  `kVisibilityChunkSize = 256` candidates and one threadgroup; sparse dispatches use global
  chunks, dense dispatches use run chunks from the CPU chunk table so no threadgroup straddles runs.
- `lmx.pass.visibility.scan`: dense layout only. One threadgroup per run computes exclusive
  offsets over that run's chunks into a transient, looping with a carry when a run exceeds 256
  chunks. No atomic allocates a position.
- `lmx.pass.visibility.emit`: one thread per candidate. Sparse layout: slot equals candidate
  index; the row receives the instance row and the argument receives `instanceCount` 1 for a
  retained candidate or 0 for a rejected one. Dense layout: position equals the run's first slot
  plus the chunk offset plus the thread's in-chunk exclusive prefix, so every run is dense and in
  candidate order; the run's argument receives its retained count. Arguments are written as raw
  32-bit words in the `IndirectSmoke` pattern, never through a mirrored struct.

A retained candidate is every non-rejected one, so bypassed candidates are emitted as on the CPU.
Counters accumulate with atomics because counts are order-independent.

### Ordering, arithmetic, capacity and counters

Ordering is defined against the matching CPU submission mode: canonical run order and stable
candidate order within each run. For the same mode the GPU output equals the CPU output in the
sequence of valid row entries concatenated over runs, the per-run retained counts, and the
`indexCount`, `instanceCount`, `firstIndex` and `baseVertex` fields of every argument.
`firstInstance` follows each layout's own slot rule: candidate index in the sparse layout, the
run's first slot in the dense layout, and the CPU batched path's dense cumulative offset, which is
unchanged from M7.2. A sparse slot with `instanceCount` 0 carries defined zero fields.

The box test is specified as an ordered fp32 sequence written with explicit multiplies and adds on
both sides, never a `dot` intrinsic. The visibility kernels compile with safe math on both the
offline and runtime routes, and the CPU oracle's unit compiles with floating-point contraction
disabled, so neither side can diverge by a fused multiply-add at a plane. The fixtures place
probes one ulp inside and outside a plane.

`VisibilityParams` carries explicit row, argument and state capacities that follow the tables
under the M7.1 growth rule. Every kernel write is bounds-checked; an entry that would exceed a
capacity is dropped and counted, never written, and a truncated run's argument receives the count
that fit. Overflow is therefore impossible in production and is exercised only through a
fixture-side capacity override. The policy is to draw what fit, surface overflow in
`VisibilityStatus`, the Inspector and the console, fail a capture sequence, and refuse a scored
measurement frame. Counters per view are candidates, visible, rejected, the four bypass reasons,
emitted rows, emitted commands, overflowed rows and overflowed commands: 11 words plus one
padding word per view in `lmx.draw.counters`. Reconciliation requires candidates = visible +
rejected + Σbypassed and emitted rows = visible + Σbypassed − overflowed rows.

### Graph, buffers and readback

`lmx.draw.rows` and `lmx.draw.args` gain `storageWrite` and are imported with their recorded
terminal uses, so the graph derives the storage-write to indirect-argument barrier before the
shadow and scene passes and the cross-frame edges, under ADR 0021's rule that storage writes,
shader reads and indirect-argument reads retain distinct uses. `lmx.draw.candidates`,
`lmx.draw.runs` and `lmx.draw.chunks` are CPU-written imports; `lmx.draw.states` and
`lmx.draw.counters` are GPU-written, CPU-readable per-slot buffers; chunk counts and offsets are
graph transients. The compiled record, graph dumps and the Render Graph window show every edge.

The Renderer reads the retired slot's counters and states when `Device::beginFrame` returns,
which is the frame that used the slot three frames earlier, and fills the same `VisibilityStatus`
the CPU path fills, labelled with that retired frame number. Hierarchy badges, the selected
object's state and reason, the Visibility block and the measurement samples consume it unchanged
apart from the frame label, GPU pass timings and overflow fields. `--classify gpu
--classify-check` additionally runs the CPU oracle each frame and reports sequence, count and
argument mismatches per retired frame; it is unscored diagnostics, never a production mode.

### ICB feasibility spike

Before any adapter code, a bounded runtime spike runs on a short-lived `exp/m7.3-icb-spike`
branch under the pinned Slang 2026.14.1 and current metal-cpp, without blocking the fixed-slot
work above. Its first commit reproduces the owner's compile-success probes for native-interop ICB
encoding and argument-buffer texture arrays, which have no runtime verification yet. It then
answers three runtime questions, each with retained evidence:

- **P1, native execution.** A compute kernel using Slang's Metal native interop encodes indexed
  draws into an ICB from GPU-written visibility output, and a Metal 4 render encoder executes them
  under Metal validation with a labelled pass in a GPU capture. Whether the Metal 4 encoder family
  executes an ICB at all is a spike question, not an assumption.
- **P2, per-draw textures.** An argument-buffer texture array supplies five material textures per
  draw inside an ICB-executed draw, and a two-material two-mesh scene samples them correctly.
- **P3, reliability.** 900 frames across the three paced slots with per-frame reset and
  re-encode complete with no GPU restart, fault or validation error, the M5.6 stress length.

Pass means all three hold and the P2 image equals the fixed-slot image of the same scene exactly.
The outcome is recorded in a dated research note under `docs/research/` and an immutable tag
either way. A fail or an unresolved lowering gap leaves ICB optional, retains the evidence and
does not expand the M7 boundary; ADR 0012 is not read as proof of impossibility. The Slang pin
does not move in this slice; an upgrade needs its own ABI adaptation.

### Capability-selected ICB adapter

Only if the spike passes, `SubmissionMode::IndirectCommands` (`--submission icb`) becomes a
fourth mode, valid only with `--classify gpu` and offered only with the capability.

- **Capability.** `DeviceCapabilities` gains `indirectCommands` with support and a maximum
  command count, reported from the backend's actual creation of a probe buffer, never inferred
  from the device family or the backend name.
- **RHI surface.** `IndirectCommandBuffer`, created with a maximum command count and the render
  pipeline set it may reference; `CommandList::executeIndirectCommands(buffer, first, count)`
  inside a render pass; a reset inside a copy pass; and `TextureTable`, an argument-buffer texture
  array with stable indices. Public headers keep no Metal types, creation returns `Result`, misuse
  asserts and every object is labelled.
- **Scene data.** `MaterialRow` stays 112 bytes. A separate paced `lmx.scene.materialTextures`
  table, 32 bytes per material row holding five texture-table indices, exists only while ICB mode
  is active, so the shared row ABI and its oracle are untouched. Texture fallbacks resolve to the
  same fallback textures the direct path binds, placed in the table.
- **Emit.** The same classify and scan output feeds `lmx.pass.visibility.emitCommands`, which
  writes one command per run with the run's pipeline index, index range and compacted instance
  range; command index equals run index, so the ordering contract holds. Commands inherit the
  pass's buffer bindings; the CPU issues one execute per view, declared as an indirect read.
- **Shaders.** ICB pipelines are separate scene and shadow entries that read textures through the
  table index instead of per-draw bindings, mirrored across the exposure twins under the
  shader-style rule. That is the disclosed cost: six additional entries.
- **Fallback.** Unsupported capability or creation failure falls back to GPU classification with
  batched fixed slots and reports it in status like the ADR 0017 vendor fallback. Fallback fails a
  capture sequence and refuses a scored measurement, so evidence never silently changes mode.
  The adapter adds no bindless material rows, no descriptor indexing beyond the texture table and
  no GPU pipeline selection beyond the run's precomputed pipeline.

### Editor, CLI and measurement surface

The Rendering Inspector's Visibility block gains a Classifier selector beside the culling toggle,
the retired-frame label for GPU results, overflow fields and the `lmx.pass.visibility.*` GPU
times; the ICB mode appears only with the capability. Formatting stays CPU-testable AppModel
logic. `MeasurementRun` moves its report to schema version 2, adding the classify mode, the
visibility pass timings as GPU preparation, candidate, chunk, state and counter bytes, allocated
list and argument bytes, retired counters, overflow flags and check-mode mismatch counts.
`Tools/Bench/visibility_paired.py` adds GPU-versus-CPU controls under indirect and under batched,
and ICB-versus-batched when built, on the frozen six-workload set with the 12/32/256 protocol; it
reports every cell with its interval and applies no decision rule. CPU commands are disclosed as
candidates in the sparse layout and runs in the dense layout regardless of visibility.

## Verification plan

### Fixtures

CPU tests under `[render][visibility]`, `[render][submission]` and `[app]`:

- **Candidate order and positions:** candidate tables, run descriptors and chunk tables for both
  layouts match hand-built expectations, including sparse instance rows after removal and
  single-instance runs; a CPU model of chunk offsets and in-chunk prefixes pins the exact dense
  position formula and the sparse identity, including a run longer than 256 chunks.
- **Counters and overflow:** reconciliation rules and the drop-and-count policy are pinned on the
  CPU model, including a truncated run's argument count.
- **Options, report and display:** `--classify` and `icb` parse, conflict and default as
  specified; schema version 2 is pinned; scored refusal on overflow, fallback and check mode is
  tested; Classifier selector, retired-frame label, overflow and GPU timing fields are pinned.

GPU fixtures under `[gpu][visibility]`, all under Metal validation:

- **Set and sequence parity:** VisibilityLab at three rail times with its boundary lane, plus
  instances placed one ulp inside and outside a plane: GPU states, valid row sequence, per-run
  counts, defined argument fields and counters equal the CPU oracle exactly in both layouts.
- **Multi-chunk determinism:** one run of several thousand instances with a known visibility
  pattern compacts to the CPU sequence exactly; two frames with identical inputs are byte-identical.
- **Argument ABI and overflow:** emitted raw words match `DrawIndexedIndirectArgs` field for
  field; the capacity override proves dropped entries are never written and are counted.
- **Overlap and retirement:** four frames with changing visibility and GPU writers and no
  `waitIdle`; each slot reads back the last frame that used it; growth mid-flight retires old
  buffers at the last prepared frame + 3; counters read at `beginFrame` name the correct frame.
- **Attachment exactness:** the M7.2 contribution fixture extended to GPU classification: HDR,
  depth, motion and reactive attachments agree exactly at both render scales and all jitter phases.
- **ICB, if built:** capability probe, execute parity against batched fixed slots, texture-table
  sampling, fallback reporting, and the 900-frame stress on the production path.
- **Checkpoint A** runs unchanged. ADR 0009 records barrier sufficiency, not necessity, so the GPU
  writer's evidence is a green run plus a labelled capture of the derived barrier.

### Output preservation and comparison rule

Parent and candidate release binaries are frozen on the same device before and after the change,
with raw evidence outside the source tree. The rules are fixed here before any measurement:

- **Same binary, GPU versus CPU classification** under the same submission mode, on the
  fifteen-image matrix: exact SHA-256 equality in every image, a gate separate from the sequence
  equality above, not a consequence of it.
- **Same binary, ICB versus batched fixed slots**, if built: exact equality on the fifteen images.
- **Parent M7.2 versus candidate defaults**, which are unchanged: the M7.1 criteria as recorded in
  its record, including the accepted `vendor-quantization-v1` profile for MetalFX images only, the
  frame-32 TemporalLab motion readback within 1/4096 UV, and the three-frame Native TAA sequence
  under the strict criterion.

A failing image is recorded as a failure with its numbers; thresholds are never loosened after
measurement, and any exception is the owner's explicit decision. The unresolved M7.2
process-repeatability observation is neither an excuse nor an explanation for a failure here.

### Regression inventory

Build, `xmake test`, the GPU suite under `MTL_DEBUG_LAYER=1`, format, `xmake policy` with the
module, header, comment and shader-import checks, and the unchanged `[checkpoint-a]` filter all
pass. Renderer-driven `Tests/Golden/frame-*.txt` are unchanged for the default CPU path; new
goldens pin the GPU-classified frame with its passes and derived barriers. `CaptureSchemaTests`
pins the new records. A validation-clean editor session switches every catalog scene under GPU
classification, toggles culling, each layout and the check mode with the image unchanged to the
eye, inspects a rejected object's badge and reason from a retired frame, and completes one
interactive measurement. One headless paired collection over the frozen set with the new controls
is completed on the frozen device with variation reported; its numbers are diagnostics, not a
performance conclusion.

M7.3 adopts no default. CPU classification with indirect submission remains the default; making
a GPU-generated path the default is a separate owner decision under the roadmap's production-
evidence rule and ADR 0012's bar: at least 15% median improvement against both direct and batched
at two adjacent N scales with paired 95% intervals above zero and guard intervals above the loss
margin. Native-host timings do not select a default.

## Known limits and design boundaries

- The shadow view stays unculled; per-cascade culling is M8.1 scope over this view mechanism.
- Fixed-slot modes still bind textures and select pipelines per run on the CPU and issue one
  command per candidate or run regardless of visibility; that encoding is reported, not removed.
- No occlusion, HZB, cluster LOD, bindless material rows or descriptor indexing; M7.4 and M9 own
  those. The atomic compaction variant is deferred until production measurements identify
  compaction as a bottleneck. Dense dispatches over many single-instance runs are small;
  utilization is measured, not tuned.
- ICB exists only if the spike passes, only on devices reporting the capability, and never as a
  default. The Slang pin is unchanged.
- GPU results reach the editor three frames late by construction; the frame label says which.
  Editor measurements include UI and presentation and are never scored.
- Existing image-parity exceptions, failed gates and manual/capture follow-ups from M6.4, M6.5,
  R1.3, R1.5, M7.1 and M7.2 carry forward unchanged; this slice neither closes nor broadens them.
