# M6.5 — Display boundary and EDR evaluation

**Status**: Implemented

The owner accepted closure on 2026-09-13 with the historical screenshot-drift exception below.
The SDR implementation is the current baseline; EDR adoption is deferred.
[ADR 0019](../decisions/0019-display-domains-and-edr.md) records the display domains and binding
reference-white/headroom policy for any future extended-range view.

## Implemented behavior

The Renderer exposes one opaque eight-bit SDR BT.709/sRGB/PBR Neutral display domain. Inspector
shows it with the encoded SDR UI rule, backing scale and settled 1:1 viewport mapping. Scene,
exposure, temporal and display shaders are unchanged, and the production RHI remains SDR-only.

Screenshots accept PNG or BMP by extension. PNG adds standard SDR color chunks and display/frame
text metadata without a pixel transform. Sequences default to PNG with an explicit BMP override;
manifest v2 records display, container and UI absence. The comparison tool accepts legacy v1 and
both containers, rejecting reused frame filenames. Capture serialization is CPU-testable App logic.

## Open parity investigation

An independent sibling worktree on `exp/m6.5-hash` isolates the existing scene-color variation;
production rendering and all reference hashes remain unchanged. Per-frame texture readback,
including deferred file writes and HDR-only variants, suppresses drift in bounded samples.
A last-frame-only diagnostic matrix still matches 13/15, now including a native half-scale
failure. Broad encoder barriers also fail to eliminate native drift. The first broad-barrier
vendor variant used invalid fence consumer stages and is excluded; corrected individual matches
are insufficient to establish a repair.

GPU integer checksums first differ in scene HDR at frame 25 in one native pair and frame zero in
two others, then propagate through history. Motion, reactive, depth and, where recorded, shadow
checksums remain equal for all 32 frames. A first-frame HDR snapshot independently confirms 208
differing pixels at x=228–387, y=213–305, maximum 0.005828857421875 in pre-exposed linear units.
Checksums are post-render observations, not cryptographic proof or instruction-level attribution.

Three 32-frame native-half repeats per diagnostic narrow the differing path further:

| Diagnostic | Observed repeatability |
|---|---|
| Diffuse texture sample only | Scene HDR and subsequent history vary; auxiliary stages agree |
| Shadow visibility only; world position only | All six stage checksums agree across all frames in each three-run group |
| Diffuse with anisotropy one; GPU-optimized contents disabled for uploaded textures or targets; tile size 32 | Each variant still varies |
| Explicit `SampleGrad` using `ddx`/`ddy` | Still varies |
| U and V, each emitted as all four FP32 bytes | Each three-run group agrees for every frame and recorded stage |
| `ddx(U)`, `ddy(U)`, `ddx(V)` emitted as FP32 bytes | Scene HDR and history vary; `ddy(V)` is stable in its three-run group |

Writing explicit `SV_Depth = input.position.z` makes diffuse-only and `ddx(U)` byte output
stable across three repeats each (all 192 stage records per run). However, compared with the
prior diffuse-only output, depth, HDR and history change at every frame and the BMP hash changes.
This variant alters rendering semantics and is not a compatible repair. Explicit
`[earlydepthstencil]` without the depth write still varies in both three-run groups.

The byte diagnostics preserve all 32 payload bits through the half-float scene target; stage
checksums observe their outputs. This localizes the reproduced symptom to the existing scene
diffuse/gradient path. It does not establish engine API misuse, benign Apple behavior, or one
cause for every historical mismatch. Stable groups are bounded samples, including no observation
of hidden helper-lane values. The strict fifteen-hash gate remains unmet; the owner-authorized closure exception below
does not reclassify it as passed.

GPU shader validation separately reports bloom texture-usage mismatches. Its default zero-fill
can alter results, so that diagnostic image is excluded from parity; the resource/view reporting
issue remains unresolved and is not attributed as the ordinary scene-HDR drift's cause.

## EDR evaluation

An isolated `exp/m6.5-edr` worktree provides extended-linear float presentation, current-headroom
policy, linear UI bounded at white one, direct calibration patches, float readbacks, SDL/NSScreen
crosschecks and paired windows. The final 360-frame SDR/EDR runs are validation-clean; current
headroom settles near 11.8033 and the chosen peak approaches four. The owner reports clearly
brighter EDR highlights and distinguishable 1/2/4 patches. On 2026-09-13 the owner explicitly
confirms equally bright white UI text at the same system brightness, superseding earlier
impressions. This passes the bounded subjective visual check; it is not a photometric measurement
or independently verified by UI-free readbacks. No per-preset numerical record or photograph is
claimed. A stable float readback reaches 3.998046875; forcing headroom to one yields maximum 1.0
and zero channels above one, then restores peak four. This verifies range fallback only, without
recreating the float layer or changing the EDR metadata domain. The proposed peak-scaled Neutral
curve darkens midtones by 63.84% at input 0.18 and 26.09% at 0.5 (peak four, display-linear oracle
output), supporting the defer decision until a future view has an intentional appearance and
production comparison. See ADR 0019 for startup-reporting, curve, capture and cost limits.
