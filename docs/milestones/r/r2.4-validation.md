(`https://github.com/AmanThuL/rojo-rhi.git`) pinned to `8da2a79e82ef66ed67d9642f0f3c5a74d20c33a8`

## Fresh-clone gates

This sandbox's outbound network to `github.com`/GitHub Releases ran at a few hundred kilobytes per
minute during this record, so the two gates below split into what actually finished and what did
not.

- **A fresh `git clone --recursive` of the pushed `r2.4-mount` branch, then a build:**
  `git clone --recursive --branch r2.4-mount https://github.com/AmanThuL/Luminex.git` into an empty
  directory completed, checked out `9bda119`, and populated `RojoRHI` at
  `8da2a79e82ef66ed67d9642f0f3c5a74d20c33a8` with no dirty or uninitialized marker in
  `git submodule status` — the clone and the submodule pin are exactly as pushed
  (`luminex-fresh-clone-head.txt`). Its network-fetched pinned dependencies (Sponza, the HDRI,
  fonts, ThirdParty) were **not** independently re-fetched by `xmake setup` in this session, for the
  same network reason as `rojo-rhi` below; `ThirdParty` and `Assets/Fetched` were instead seeded by
  copy from an already-set-up worktree, the same shortcut `AGENTS.md`'s worktree guidance already
  documents. From that state, `xmake f -m release -P .`, `xmake build -P .`, `xmake build -P .
  Tests`, `xmake build -P . RojoRHITests` and `MTL_DEBUG_LAYER=1 xmake test -P .` all passed: **100%
  tests passed, 0 failed out of 4** (`luminex-fresh-f.log`, `luminex-fresh-build.log`,
  `luminex-fresh-tests-build.log`, `luminex-fresh-rojorhitests-build.log`, `luminex-fresh-test.log`).
  This proves the pushed branch, its submodule pin and its build wiring are correct from a clean
  checkout; it does not independently prove the dependency-fetch half of `xmake setup` on a slow
  link, which is the part this record could not exercise.
- **A fresh `rojo-rhi` clone, no Luminex present, then `xmake setup`:** an anonymous
  `git clone https://github.com/AmanThuL/rojo-rhi.git` completed immediately and checked out
  `8da2a79` at `HEAD` (`rojorhi-fresh-clone-head.txt`) — confirming public, credential-free access
  and the exact pinned commit. `xmake setup` then fetched metal-cpp successfully but failed
  fetching the 55.2 MB Slang archive: `curl`'s own `--max-time 600` elapsed with roughly 500 KB
  transferred (`execv(curl ...) failed(28)`, `rojorhi-fresh-setup-error.txt`) — a timeout of this
  sandbox's `curl` call, not a `rojo-rhi` or mount defect. `xmake f`, `xmake build RojoRHITests`,
  `xmake test`, `xmake format --check` and `xmake policy` were **not** run against this fresh
  checkout as a result. Stronger evidence than a sandbox re-run already exists for this exact
  commit: `rojo-rhi`'s own hosted CI ran `xmake setup`, configure, build, `RojoRHITests/unit` and
  `xmake format --check` against `8da2a79` before it merged (`rojo-rhi#4`, both jobs green: policy
  5s, build-test 2m4s). R2.1's and R2.4a's own accepted standalone evidence additionally exercised
  the same path on earlier commits of the same history.
- **Hosted CI on the pull request** (`.github/workflows/ci.yml`, every `actions/checkout@v5` step
  passing `submodules: true`) runs its own fresh checkout, including the submodule, on GitHub's own
  network rather than this sandbox's; its `policy` job also runs `check_submodule_pin.py --fetch`.
  Hosted runners lack Metal 4, so it cannot stand in for `MTL_DEBUG_LAYER=1 xmake test`; that GPU
  requirement is unchanged from every prior milestone and was met by this record's own worktree and
  fresh-clone runs above, not by CI.

## Limits

- This record's Tier 2 comparisons cover one frame, one capture and one short sequence of Sponza;
  they are not a full re-run of M6.4/M6.5/M7.x's per-scene image suites, which R2.2 and R2.3 also
  did not repeat for a build/CI-only change.
- The capture-schema and `gputrace_dump.py` comparison used one capture per side rather than the
  repeated-capture flake probe R2.2 used to characterize its one unattributed difference; this
  record's single pair was clean, so the probe was not run.
- Gate G's own `xmake policy` task body is not exercised from this nested worktree (the documented
  gotcha: `xmake policy` resolves to the outer checkout's root when run inside a worktree); every
  checker it invokes was instead run directly, as G and `AGENTS.md`'s worktree guidance specify.
  The policy task's own run should be confirmed from a non-worktree checkout before merge, as R2.4b's mount task already noted.
- `RojoRHI/`'s own checkers, format/policy tasks and Python suite were not re-run standalone from
  inside this mount as part of this record; they are `rojo-rhi`'s own CI's responsibility now, and
  that CI already ran on the component's own repository pull requests before the mount (R2.1, R2.4a
  preparation). A bare copy-out standalone gate for the mounted commit specifically was not
  repeated here.
- `rojo-rhi`'s clean-clone `xmake setup` was blocked by this sandbox's network, not by anything
  under test; the same fetch has already succeeded in this environment for Luminex's own setup
  (`ThirdParty/slang`, present in the worktrees this record built from). The better evidence for
  this exact pin already exists rather than being outstanding: `rojo-rhi`'s own hosted CI ran
  `xmake setup`, configure, build, `RojoRHITests/unit` and `xmake format --check` against
  `8da2a79` before merge (`rojo-rhi#4`, both jobs green: policy 5s, build-test 2m4s). A sandbox
  re-run with normal network throughput would only repeat that result.
