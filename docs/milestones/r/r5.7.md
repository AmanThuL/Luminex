## Item A: bindless material rows and one draw root per pass

**Change.** `MaterialRow` grows from 112 to 144 bytes: five `uint` sampled-view indices
(`baseColorView`, `normalView`, `metalRoughView`, `occlusionView`, `emissiveView`) and three zero
pads. `Scene::prepareFrame` resolves each view on the CPU, a missing texture to the scene's white
or flat-normal fallback, which `Scene::finalize` now creates; the Renderer no longer owns material
fallbacks. The four `ScenePass*` twins and `ShadowPassMask` read the views from the row, so the
draw roots lose them: `SceneDrawRoot` and `ShadowDrawRoot` shrink to 16 bytes
(`pass`, `firstEntry`, `indirect`).

- Indirect and batched submission push one draw root per pass (`indirect = 1`, the shader reads
  `drawId`), so each run is a cached `setPipeline` plus `drawIndexedIndirect`.
- Direct submission still pushes one root per run for its `firstEntry`, because a vertex entry
  cannot read the base instance (RojoRHI ADR 0024).
- The shadow pass sets its depth bias once, after its first pipeline bind, instead of once per
  draw; the values persist across `setPipeline` to the end of the pass (RojoRHI spec 06, dynamic
  state). Every shadow pipeline enables depth bias.
- A material whose texture changes gets a different view, so its row differs and every paced slot
  is rewritten; a removed texture already retires three frames later, after the last slot that
  names it.
- One 16-byte root serves both submission paths, rather than `ScenePassRoot` itself on the
  indirect path: the shaders keep one root type, and the GPU work is unchanged.

`SelectionMask` and `OcclusionReference` keep their own per-object roots with a diffuse view; they
draw one object or a reference pass, not the scene's runs.

**Cost removed.** On indirect and batched submission, per draw: one frame-data suballocation, one
48-byte (scene) or 32-byte (shadow) copy and one `setRoot`; per shadow draw, one `setDepthBias`.
VisibilityLab at 4,096 instances issues about 7,600 such draws a frame, at 16,384 about 26,100.

`FixtureSceneView`, the test support that draws test-owned textures through a real scene, now also
writes those textures' views into the prepared slot's material row, where the scene alone would
name its fallbacks.

|---|---|
| `scene table structured-buffer ABI preserves every field and row stride` | the oracle writes 124 words a row, the eight new material words included |

## Item B: fragment-only raster reads, parked

The branch let a raster pass declare reads that only its fragments use (the scene's shadow map,
light lists and exposure; the fullscreen passes' inputs), so they wait at the fragment stage and the
scene's vertex work no longer waits for light clustering and shadows. Against `main` the frame is
cheaper: `frameGpuMs` Sponza 2.91 [2.26, 3.52], LightLab 1.20 [0.92, 1.58], VisibilityLab 6.35
[5.25, 7.21], TemporalLab too wide to judge. But `gpuSumMs` is 36–65% worse in every scene, all of
it in the `lmx.pass.display` scope (0.04 → 0.48–1.18 ms): that scope now opens before the work it
waits on and absorbs the wait. TemporalLab's `sceneGpuMs` is also 10.06% [5.67, 17.05] worse, which
its frame time is too wide to contradict. With B, `gpuSumMs` against frozen v1, which reports no
frame time, fails in all five scenes (11–54% worse), so R5's cost gate cannot pass. The work waits
on [#109](https://github.com/AmanThuL/Luminex/issues/109) until that gate rates frame GPU time.

## Item C: counted multi-draws

The probe counted every indirect and batched pipeline group of the scene and shadow passes,
against A. On Metal 4 a counted draw runs an encode kernel into an indirect command buffer, a fixed
cost per group and a saving per record. VisibilityLab gained: N4096 `encodeMs` 39.85
[39.02, 40.62] and `frameGpuMs` 19.19 [18.50, 19.60]; N16384 indirect `frameGpuMs` 34.11
[33.85, 34.53]. Sponza's `frameGpuMs` was −2.40 [−4.50, −1.32], which fails the rule that frame
time is not worse in any cell, and `shadowGpuMs` was flagged in both scenes (−8.51 and −21.82).
The narrower form C′ counts only large scene groups and leaves the shadow pass unchanged; it
follows in the next pull request with its own timing.

## Item D: static pass roots, dropped

After item A the scene and shadow draws push one root per pass, which was D's per-draw half. The
per-pass half rebuilds about 40–60 roots a frame at about 0.1 µs each, most of them carrying
per-frame addresses that change anyway; a persistent root would save about 1–2 µs, about 1% of a
light scene's encode, below what a 12-pair interval resolves there, at the cost of
persistent root buffers per paced slot. Revisit only if a CPU profile of a light scene shows
`uploadFrameData` above 5% of encode.
