# R5.7 — Optimization

**Status**: Implemented (items A and C′, 2026-11-09; B parked, D dropped)

R5.7 makes the v2 frame cheaper where paired evidence shows a win.
[Part III](../../roadmap/codebase-rojorhi-port.md#r57--optimization) owns the outcome and the exit
gate; this record keeps each item's change, its evidence and its verdict. Each item is one pull
request, gated by [R5's parity gate](r5.md#parity-gate) 1–3 against the frozen v1 build, and kept
only if its paired timing shows the win named below.

| Item | Verdict |
|---|---|
| A: bindless material rows, one draw root per pass | kept |
| B: fragment-only raster reads | parked: frame time wins, but the cost gate's `gpuSumMs` fails against v1 |
| C: counted multi-draws per pipeline group | the all-groups probe failed its rule; C′, scene groups of at least 512 runs, kept |
| D: static pass roots built once | dropped: below measurement resolution |

## Item A: bindless material rows and one draw root per pass

**Change.** `MaterialRow` grows from 112 to 144 bytes: five `uint` sampled-view indices
(`baseColorView`, `normalView`, `metalRoughView`, `occlusionView`, `emissiveView`) and three zero
pads. `Scene::prepareFrame` resolves each view on the CPU, a missing texture to the scene's white
or flat-normal fallback, which `Scene::finalize` now creates; the Renderer no longer owns material
fallbacks. The four `ScenePass*` twins and `ShadowPassMask` read the views from the row, so the
draw roots lose them: `SceneDrawRoot` and `ShadowDrawRoot` shrink to 16 bytes
(`pass`, `firstEntry`, `indirect`).

- Indirect and batched submission push one draw root per pass (`indirect = 1`, the shader reads
  `drawId`), so each run is a cached `setPipeline` plus `drawIndexedIndirect`.
- Direct submission still pushes one root per run for its `firstEntry`, because a vertex entry
  cannot read the base instance (RojoRHI ADR 0024).
- The shadow pass sets its depth bias once, after its first pipeline bind, instead of once per
  draw; the values persist across `setPipeline` to the end of the pass (RojoRHI spec 06, dynamic
  state). Every shadow pipeline enables depth bias.
- A material whose texture changes gets a different view, so its row differs and every paced slot
  is rewritten; a removed texture already retires three frames later, after the last slot that
  names it.
- One 16-byte root serves both submission paths, rather than `ScenePassRoot` itself on the
  indirect path: the shaders keep one root type, and the GPU work is unchanged.

`SelectionMask` and `OcclusionReference` keep their own per-object roots with a diffuse view; they
draw one object or a reference pass, not the scene's runs.

**Cost removed.** On indirect and batched submission, per draw: one frame-data suballocation, one
48-byte (scene) or 32-byte (shadow) copy and one `setRoot`; per shadow draw, one `setDepthBias`.
VisibilityLab at 4,096 instances issues about 7,600 such draws a frame, at 16,384 about 26,100.

`FixtureSceneView`, the test support that draws test-owned textures through a real scene, now also
writes those textures' views into the prepared slot's material row, where the scene alone would
name its fallbacks.

**Tests with changed expectations** (case counts unchanged):

| Case | Change |
|---|---|
| `scene table structured-buffer ABI preserves every field and row stride` | the oracle writes 124 words a row, the eight new material words included |
| `Scene texture fallbacks preserve factors and stale texture handles fail lookup` | also checks the row's views: fallbacks first, the material's texture after retargeting |
| `renderer registers the four uniform struct layouts` | `MaterialRow` 144 with the view offsets; both draw roots 16 |

**Correctness.** Images are byte-identical to `main` before the change, which is the expectation:
the views, samplers and UVs are the same, only where the shader reads the indices from changed.

## Item B: fragment-only raster reads, parked

The branch let a raster pass declare reads that only its fragments use (the scene's shadow map,
light lists and exposure; the fullscreen passes' inputs), so they wait at the fragment stage and the
scene's vertex work no longer waits for light clustering and shadows. Against `main` the frame is
cheaper: `frameGpuMs` Sponza 2.91 [2.26, 3.52], LightLab 1.20 [0.92, 1.58], VisibilityLab 6.35
[5.25, 7.21], TemporalLab too wide to judge. But `gpuSumMs` is 36–65% worse in every scene, all of
it in the `lmx.pass.display` scope (0.04 → 0.48–1.18 ms): that scope now opens before the work it
waits on and absorbs the wait. TemporalLab's `sceneGpuMs` is also 10.06% [5.67, 17.05] worse, which
its frame time is too wide to contradict. With B, `gpuSumMs` against frozen v1, which reports no
frame time, fails in all five scenes (11–54% worse), so R5's cost gate cannot pass. The work waits
on [#109](https://github.com/AmanThuL/Luminex/issues/109) until that gate rates frame GPU time.

## Item C: counted multi-draws for large scene pipeline groups

**Probe.** The probe counted every indirect and batched pipeline group of the scene and shadow
passes, against A (window 1). On Metal 4 a counted draw runs an encode kernel into an indirect
command buffer instead of native draws, so its cost has a fixed part per group and a part per
record (positive is cheaper):

| cell | records per pass (scene + shadow) | scene GPU | shadow GPU | `frameGpuMs` |
|---|---|---|---|---|
| Sponza | 9 + 25, one group each | −0.017 ms | −0.013 ms | −2.40 [−4.50, −1.32] |
| VisibilityLab N4096 | 3,477 + 4,096, three groups each | +0.32 ms | −0.095 ms | 19.19 [18.50, 19.60] |
| VisibilityLab N16384 indirect | 9,717 + 16,384 | +1.97 ms | +0.068 ms | 34.11 [33.85, 34.53] |

VisibilityLab N4096 `encodeMs` was 39.85 [39.02, 40.62] cheaper. Sponza's frame was worse with an
interval excluding 0, which fails the rule that `frameGpuMs` is not worse in any cell, and
`shadowGpuMs` was flagged in both scenes (−8.51 and −21.82), so the probe as built was not kept.

**Change (C′).** On indirect and batched submission, `buildDrawSubmission` moves every scene
pipeline group (opaque, masked single-sided, masked double-sided, as the scene stage chooses its
pipelines) of at least `kCountedDrawMinRuns` = 512 runs to the front of the scene list, in group
order, and records its counted draws in `DrawList::countedDraws`. `encodeDrawRuns` runs each
covered run's callback (one pipeline bound, every access declared) and issues one
`drawIndexedIndirect` over the group's consecutive records with no count. A group above RojoRHI's
Metal 4 `maxDrawIndirectCount` (65,536) is split evenly into the fewest draws. The other runs
follow in their original order as lone draws, and shadow runs never move: below the threshold,
and in every shadow pass, the command stream is item A's. Counted draws lead because a lone draw
opens Metal 4's render encoder, which a later counted draw would split.

**Threshold.** The probe's scene pass gains about 0.1 µs of GPU time per record at N4096 (0.2 µs
at N16384) and pays about 17 µs per small group (Sponza), so a group breaks even near 160 records.
512 keeps about three times that margin, is 13 times the largest light-scene pass (38 records), so
Sponza, MaterialLab, TemporalLab and LightLab keep item A's command stream exactly, and lies below
every VisibilityLab group at the measured cameras (about 870–1,740 records at N4096). Shadow draws
are depth-only and cheap natively: counting them lost GPU time at 25 and 4,096 records and gained
4% only at 16,384, so the shadow pass keeps lone draws.

**Tests.** Three `[submission]` cases: groups below the threshold keep the builder's order and
argument offsets; a group at exactly 512 runs leads as one counted draw with consecutive arguments
while 256-run groups and the shadow list stay as they were, and three groups at the threshold
become three counted draws in group order; groups of 65,536, 65,537 and 131,077 runs split into
one, two and three even draws of at most 65,536.

**Correctness.** Images are byte-identical to item A: the draw order changes only inside the scene
pass of VisibilityLab, whose equal-depth ties do not change a pixel. Release and Debug
`--rhi-validation` windowed smokes pass as A's do.

**Timing.** Kept (window 2). Against A, `parent_paired.py`: VisibilityLab N4096 indirect

not flagged, and contradicted by the frame). The light scenes draw the same counts and every

## Item D: static pass roots, dropped

After item A the scene and shadow draws push one root per pass, which was D's per-draw half. The
per-pass half rebuilds about 40–60 roots a frame at about 0.1 µs each, most of them carrying
per-frame addresses that change anyway; a persistent root would save about 1–2 µs, about 1% of a
light scene's encode, below what a 12-pair interval resolves there, at the cost of
persistent root buffers per paced slot. Revisit only if a CPU profile of a light scene shows
`uploadFrameData` above 5% of encode.
