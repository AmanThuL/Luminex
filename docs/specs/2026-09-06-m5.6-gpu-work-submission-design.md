# M5.6 — GPU Work-Submission Experiment — Design Spec

**Date**: 2026-09-06
**Status**: Frozen — non-normative
**Boundary authority**: [roadmap](../roadmap.md), M5.6. This spec decomposes its experiment,
measurement and disposal boundary; it does not authorize production GPU-scene or RHI changes.
The [implementation plan](../plans/2026-09-06-m5.6-gpu-work-submission.md) sequences this design.
Freeze the resolved manifest before scored collection.

**Terminal disposition, 2026-09-06:** the user approved closing this experiment as reliability
failure / DEFER with no accepted performance conclusion. [ADR 0012](../decisions/0012-gpu-submission-defer.md)
and the roadmap supersede the requirement to finish the full measurement matrix for this closure
only. They do not declare any failed/missing gate passed or relax future adoption requirements.
The sections below preserve the original experimental contract; further diagnosis is separate work.

## 1. Purpose and baseline

Determine when GPU work generation repays its preparation cost on Metal 4. Produce a reproducible
break-even report and an adopt/retain/defer decision for M7, not a universal GPU score. Negative
results and a documented unavailable ICB path are valid outcomes.

The merged M5.4/M5.5 baseline provides exact compiled-frame inspection, a detached graph window,
and corrected Metal lifetime handling. Its production renderer still submits per-object draws.
The public RHI accepts GPU-written indirect argument records, but does not expose ICB execution,
persistent CPU buffer writes, or an explicit direct-instancing overload. These distinctions are
visible in [CommandList](../../RHI/Include/RHI/CommandList.h),
[Buffer](../../RHI/Include/RHI/Buffer.h), and [Device](../../RHI/Include/RHI/Device.h).

## 2. Questions and non-goals

- H1: GPU-written arguments alone can reduce visibility work without reducing CPU draw calls.
- H2: GPU-encoded ICBs reduce CPU command work sufficiently to offset reset/generation/execution.
- H3: visibility, draw size and material bins change the break-even point; batching may win first.
- H4: the supported routes preserve visibility, image output, retirement and capture quality.

No production scene identities, public RHI extensions, general bindless resources, temporal/HZB
occlusion, mesh/task shaders, DGC, Work Graphs, second backend, neural shader, or editor redesign.
No purchase is necessary to close this Metal experiment. Other hardware can support later studies.

## 3. Isolation and comparison host

All implementation lives on `exp/gpu-work-submission` under `Experiments/GpuSubmission/`, namespace
`lmx::experimental::submission`. A root build include registers non-default targets; no source in
`Source/`, `RHI/`, production `Shaders/`, or fetched dependencies is modified. Do not extend or
repurpose the frozen NoApi experiment or the maintained FrameData benchmark.

| Proposed target | Ownership and dependency boundary |
|---|---|
| `GpuSubmissionModel` | Manifest, geometry/input generation, CPU oracle, results; standard C++ and glm, no Metal/RHI headers |
| `GpuSubmissionMetal` | Private fixed-workload Metal 4 executor; Core and metal-cpp; owns all native objects |
| `GpuSubmissionReference` | Untimed production RHI/RenderGraph adapter; public RHI only; no native casts |
| `GpuSubmissionBench` | CLI over the model and adapters; no SDL, ImGui, swapchain or fetched scene assets |
| `GpuSubmissionTests` | Catch2 model, ABI, reference and native validation cases; GPU cases separately tagged |

All scored variants use the same native host, device configuration, storage modes, shader
artifacts, allocator discipline and binding path. This controls the public RHI's missing mapped
write facility without timing per-frame resource creation against persistent GPU buffers. It
measures execution mechanisms, not the cost of Luminex's RHI or a promised production speedup.
The unchanged RHI adapter anchors image and graph semantics in separate correctness runs.
Destroy reference resources before scoring. Each variant creates and tears down its own resource
set on the same physical GPU; no previous variant's resident working set remains in a timed run.

Native objects stay inside the Metal adapter, with its own device/queue and three frame slots;
no pointer crosses into the production adapter. This is a workload executor, not another RHI.
Reuse established algorithms and lifetime rules without copying the entire backend.

## 4. Shader and ICB feasibility gate

All scored shader sources are Slang under the experiment's `Shaders/` directory, compiled using
the repository's pinned Slang-to-MSL flow. Use separate target output directories and track every
experiment shader import. Vertex/fragment artifacts are shared by direct, indirect and ICB modes.
The instancing control may take a uniform selection branch in that same shader; record it as a
batching control, not a pure submission-only equivalence claim.

Before implementing the full ICB route, prove a tiny offscreen generate/execute/readback case:

1. Confirm native ICB creation and execution with the pinned Metal headers and runtime.
2. Compile the GPU command-generation kernel from Slang; inspect the emitted MSL and bindings.
3. Validate inherited or explicit pipeline/buffer binding, reset-to-generation and
   generation-to-execution ordering, indirect-resource residency and three-slot reuse.
4. Render alternating visible/empty frames and verify no command survives a slot's reuse.

The pinned headers expose `MTL4::RenderCommandEncoder::executeCommandsInBuffer`; that proves a
host entry point, not shader lowering or runtime correctness. Record each capability as verified,
unsupported, or unresolved, with compiler diagnostics and the minimal reproduction. Use at most
two implementation days for this probe. If it fails, close ICB as unavailable for this experiment
and complete direct/indirect results. No compiler upgrade, vendored patch, handwritten MSL
replacement or Metal 3 fallback is silently introduced to rescue the scored ICB path.

## 5. Workload and numerical contract

One versioned manifest owns all inputs; freeze its content hash, generator version and shader
hashes before measurement. Fixed defaults: seed `0x4C4D5836`, 1024×1024 offscreen RGBA8Unorm color,
D32Float reversed-Z depth (clear 0, greater comparison), no blending/MSAA, fixed exposure, no
display transform, temporal processing or post effects. Colors are synthetic scene-linear values
in [0,1], stored without sRGB encoding; this is a diagnostic signal, not the production PBR frame.

Use a planar quad tessellated 1×1 or 4×4 into T = 2 or 32 triangles, identical across objects,
separate instance transforms and conservative sphere bounds. Allocate virtual vertex ranges of
`3*T` vertices per object. Ordinary modes issue `firstVertex = objectId * 3*T`; the common vertex
shader derives the object and local vertex from `SV_VertexID`. This needs no per-draw root upload
or public base-instance extension. Check multiplication and buffer indexing before dispatch.
Both tessellations have identical silhouette, bounds and projected coverage; no degenerate or
duplicate overlapping triangles. In batched mode, local vertex ID addresses that same quad and
object ID is `visibleIds[binOffset + instanceId]`, with base instance zero and bin offset added once.

Objects occupy deterministic grid cells at distinct depth values. Place the requested visible
fraction safely inside a fixed perspective frustum and the remainder safely beyond a side plane;
avoid coplanar overlap and frustum boundaries in scored cases. The manifest serializes camera
matrices, coordinate conventions, geometry, bounds, transforms, bin membership and frame inputs.
Generate inputs once, outside timing, but include every per-frame copy/upload in CPU work.

CPU oracle: double-precision sphere/plane tests, visible iff no normalized plane distance is below
`-radius`. GPU uses float32 with the same inequalities; scored bounds stay at least `1e-3` world
units from a classification boundary. Boundary fixtures use a conservative epsilon of `1e-5`
world units on both sides; never silently drop mismatches from scored data.

| Set | Parameters | Purpose |
|---|---|---|
| Core | N = 1,024 / 16,384 / 65,536; T = 2 / 32; visible fraction = 0.1 / 0.5 / 1; B = 1 | 18 workload points, submission and geometry pressure |
| Bins | N = 16,384; T = 2; visible fraction = 0.5; B = 16 / 64 | Two more points, bounded bin overhead |
| Correctness only | N = 0 / 1 / 257; empty/full, boundary, alternating visibility, capacity limits | Degenerate inputs, stale commands and dispatch tails |

Bins use a fixed small table of linear colors and contiguous candidate ranges, one shared pipeline,
and identical per-bin bindings across ordinary modes. They test bin traversal and command overhead,
not heterogeneous shader/material compilation or bindless texture performance. Record requested
and actual visible counts (`floor(N * fraction)` inside). No additional Cartesian sweep is required.

Each run replays the same 256-frame input sequence. Every 32 frames deterministically exchange
which IDs occupy inside/outside cells while retaining the requested visible fraction. This
exercises updates and stale-command handling without temporal occlusion. All variants consume the
same sequence; input generation and the independent expected-result calculation are not timed.

## 6. Variants and two suites

| Mode | Per-frame preparation | CPU draw/execution calls |
|---|---|---|
| `direct` | CPU produces visible IDs in bin/object order | One direct draw per visible ID |
| `cpu-indirect` | CPU writes packed visible argument records into the retired slot | One indirect draw per visible ID |
| `gpu-args` | Compute writes one argument per candidate; invisible instances get count 0 | One indirect draw per candidate, including zero-count records |
| `gpu-icb` | Reset slot ICB, compute encodes visible candidates in fixed per-bin ranges | One ICB range execution per bin; no CPU visibility-count readback |
| `batched` | CPU compacts visible IDs per bin; vertex shader indexes IDs using instance ID | One instanced draw per nonempty bin |

`gpu-icb` is included only after section 4 passes. Fixed-range traversal is charged even when
most commands are empty. ICB optimization/compaction is not required; any exploratory version is
unscored until a new manifest/protocol is frozen. All counts, uploads and per-bin work are reported.

**Submission suite S:** consume the same precomputed visibility bitmap. Classifying geometry is
excluded for every mode; CPU scans/packing, bitmap transfer, GPU argument/ICB generation and any
compaction are included. This isolates preparation plus submission, not just the final API call.

**End-to-end suite E:** consume bounds, transforms and camera only. CPU modes perform frustum
culling inside CPU work; GPU modes perform it in the preparation kernel. Do not pass expected
visibility or read back a visible count to GPU modes. CPU oracle results exist only for validation.

The batched mode is the competent repeated-geometry control. A win over an unbatched direct loop
alone does not justify ICB adoption. Keep its addressing and visibility-list costs visible.

## 7. Frame graph, memory and retirement

One semantic manifest describes upload/reset, optional preparation, raster, and validation-only
readback. For the ordinary routes, a production RenderGraph fixture compiles corresponding uses
and checks schedule, indirect-argument hazards and declared sinks. ICB storage has no production
graph type: validate its native hazards separately and mark the graph fixture's coverage limit.
Do not invent an ICB buffer handle in the production graph to imply full validation coverage.
Execute the reference graph and compare its retired readback with native direct for every core
case and ordinary route. Reference updates may create/import buffers through public APIs outside
timing; retain each until retirement. Native CPU mapped writes are not fictitious GPU copy passes.

Each native frame slot owns its command allocator, mutable argument/visibility buffers, ICB if
supported, render targets and counters. Shared immutable geometry and material data live until all
submitted work retires. Before CPU writes or resets, wait on that slot's exact last completion
value. Label every object and command stage; include all indirectly reached allocations in native
residency. Barriers order reset, storage writes, indirect reads and raster consumers explicitly.
Release native members inside an autorelease pool, after draining work; follow M5.5's destructor
rule rather than relying on a pool whose lifetime ends before member destruction.

Reserve capacity before warmup; every frame writes or clears the complete live argument/command
range. Overflow fails the run with a diagnostic; no hidden truncation or timed resize is permitted.
Count high-water storage for all three slots, shared storage, ICB capacity and temporary data.
Report requested bytes separately from queryable allocated bytes; resident bytes are null unless
actually measured. No sum of requested sizes is labelled physical memory.
Each case has a 256 MiB requested-storage ceiling for one variant's complete three-slot working
set; native opaque ICB allocation is reported separately. An unbounded or unqueryable ICB cost
prevents an adoption recommendation, but does not invalidate supported ordinary-mode evidence.

## 8. Correctness and observation

Before timing, every supported mode must pass exact visible-ID set/count checks and image parity
against direct rendering for the 256-frame sequence. Compare RGBA8 channels with maximum absolute
error 1/255, no mismatched coverage pixels, and no NaN/invalid geometry. ID checks are independent
of whether tiny objects cover a pixel. Validate finite positive camera/bounds inputs and known
empty scenes. Larger output deviations require a design amendment and full recollection.

Use debug-only visibility/command bookkeeping and readback to verify GPU results; no debug writes
or readback copies enter scored shaders/runs. Capture representative empty, sparse and dense
frames under Metal validation; show generated arguments/commands and their resource bindings.
Stress 900 frames with changing visibility, slot canaries, and teardown; reject validation errors,
stale work or growth after capacity settles. Keep checkpoint A unchanged and passing separately.
Also replay the exact scored shader binaries untimed, under validation, with readback after
retirement. Require image parity and inspect generated ordinary arguments; the instrumented
visibility checks supplement this replay and cannot substitute for testing the scored artifacts.

The graph fixture can be inspected through existing model/layout logic and deterministic dumps;
this does not make the native ICB execution a production compiled frame. Native captures supply
its additional evidence. No new editor panel or capture-file browser is required. Interactive QA
uses the merged maximized/`--windowed` behavior only as an observation surface.

## 9. Measurement protocol

Release builds, validation/capture off, no UI/swapchain/readback. Record actual environment flags,
not just `DeviceDesc::enableValidation`, as well as device, OS, compiler, shader hashes, power and
thermal state. Refuse scored mode if validation or capture is enabled. Record unsupported counters
as null with a reason; do not derive command-processor utilization from timing.

- In headline/GPU-span lanes, collect 12 pairs for every other mode versus `direct`, and for
  `gpu-args`/supported `gpu-icb` versus `batched`. One pair is a fresh process with two drained runs;
  alternate AB/BA order. Each run has 32 warmup frames, then the same 256 measured frame inputs.
- Time CPU preparation and encoding after the slot wait through queue commit, including copies,
  culling, argument construction, allocator reset, bindings and native command work. Measure the
  slot wait separately. Snapshot bookkeeping outside the timed region; disclose any unavoidable
  counter overhead equally across modes. Never call an aggregate `beginFrame` duration pure encode.
- Separate paired collection lanes: `headline` has no GPU timestamp markers and supplies CPU work
  and throughput; `gpu-span` uses only common workload-boundary markers; `stages` adds preparation
  and raster markers for diagnosis. Never pool these lanes. Verify native ordering bounds the
  workload in `gpu-span`; unresolved boundaries make that metric unavailable. Apple's
  [timestamp contract](https://developer.apple.com/documentation/metal/mtl4commandbuffer/writetimestamp%28counterheap%3Aindex%3A%29)
  permits later work to have started, so marker placement alone is not a proof of that bound.
  Compare marker-enabled/disabled throughput before freezing and disclose observer overhead.
  A full span is not the sum of pass spans. Resolve after retirement and join by run/mode/frame ID.
  Stage diagnosis uses selected empty/sparse/dense cases and is unscored; record lane on every row.
- Collect sustained completed-frame throughput from first measured submission through final
  measured retirement, with warmup fully drained. Exclude final file serialization and correctness
  readback. Report finite-window fill/drain effects and waits; do not label reciprocal CPU encoding
  time as FPS or per-frame latency.
- Keep compilation and one-time allocation outside steady state but report their costs and
  storage. GPU command reset/generation every frame stays inside. Process startup does not imply
  a cold driver shader cache; that cache state is descriptive, not an adoption metric.
- Reduce each repetition to a median for CPU/GPU durations and one throughput value. Compute
  paired relative deltas and their median, plus a two-sided 95% bootstrap interval over the 12
  independent pairs (10,000 resamples, seed `0x4C4D5836`). Frames are not independent repetitions.

Retirement reporting must drain and resolve the final slots without inserting hidden GPU work
into the measured window. A missing/duplicate frame, timestamp or pair invalidates the run. Retain
all failed attempts with reasons; never drop statistical outliers after seeing the comparison.

Freeze configuration, algorithms, shaders, counter placement and schemas before collection.
Changes invalidate that collection for all compared modes. Capability probing precedes this
freeze. Exploratory workloads are labelled unscored and cannot select the production direction.

## 10. Decision rule

Correctness, retirement, capture visibility and honest capability coverage are gates. No win
overrides a failed gate. Express improvements as `100*(control-candidate)/control` for durations
and `100*(candidate-control)/control` for throughput. A material win has median at least 15% and
paired 95% interval entirely above zero; a material regression is the symmetric negative case.
Counts explain results rather than determine adoption alone.

Only `gpu-args` and verified `gpu-icb` are GPU-generation adoption candidates. Either requires,
in E, the same winning metric (CPU work or throughput) against both direct and batched controls
at two adjacent tested N scales with fixed T/B/visibility. For GPU-span and throughput, both
control comparisons must also have 95% lower improvement bounds above -15%; crossing that loss
margin is inconclusive and retains the incumbent, even if the regression is not significant.
Unavailable guard metrics defer the recommendation. Storage must satisfy section 7. Limit adoption
to that measured region; a blanket default needs the regression guards across the whole matrix.
CPU-indirect/batched findings remain control evidence. Multiple comparisons make this engineering
evidence, not universal statistical significance; report all cells and uncertainty, including losses.

**Adopt** means propose a bounded production implementation at M7's interface gate B, with a
maintained benchmark against the frozen oracle. **Retain** means the direct/batched incumbent wins
or evidence is inconclusive. **Defer** means a capability or measurement gate cannot be satisfied;
record the reproduction and required condition. Failure of optional ICB does not block the
supported indirect report or M6. No production API decision is made solely from native-host times.

## 11. Results, commands and disposal

Proposed commands, implemented by the plan rather than available in the baseline:

```text
GpuSubmissionBench --capabilities --output <directory>
GpuSubmissionBench --selftest
GpuSubmissionBench --verify --suite all --output <directory>
GpuSubmissionBench --measure --lane headline --suite S --case <id> --pair gpu-args,direct --order AB --output <directory>
python3 Experiments/GpuSubmission/Tools/paired.py --bench <absolute-binary> --output <directory>
```

The driver covers both suites and the frozen matrix. Each output bundle holds schema-versioned
environment/capability JSON, manifest/hash, per-frame JSONL, raw pairs, summary CSV/Markdown,
validation results and capture references. Paths resolve from the executable/manifest, not the
caller's working directory. Missing capabilities are explicit records, not successful zero timings.
Refuse overwriting a nonempty output directory. Keep raw bundles/captures outside the source tree.

At closure preserve the experiment at immutable tag `m5.6-gpu-submission-evidence`. Only its
conclusions, deciding ADR and a truthful `docs/milestones/m5.6.md` reach main; no experimental source
or build include does. The ADR records last verified environment, native/reference coverage and
the bounded recommendation. Update the roadmap's baseline only after the exit evidence exists.
M7 implements its own production benchmark against the retained workload/oracle; the evidence
tag never gains feature work. Close/remove the implementation plan per documentation convention.
