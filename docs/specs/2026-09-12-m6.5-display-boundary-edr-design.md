# M6.5 — Display Boundary and EDR Evaluation — Design Spec

**Date**: 2026-09-12
**Status**: Implemented

**Boundary authority**: `docs/roadmap.md` M6.5 and the M6 shared rules own the outcome,
deliverables, exit gate and deferrals. This spec decomposes that boundary without expanding it;
where wording differs, the roadmap wins. M6.5 makes the frame's three display-side domains — the
SDR output transform, the UI composite and the capture — explicit, tested data instead of implied
behaviour, and closes the macOS EDR/HDR question with a bounded, measured probe and a recorded
adopt-or-defer decision. It does not ship an EDR presentation path on `main`, change any scene,
exposure or temporal semantics, or require a display other than the development machine's own.

## Accepted closure deviations

On 2026-09-13 the owner accepted the SDR implementation with a narrow historical screenshot-drift
exception. Sections 2, 6, 9 and 13 retain the original strict hash expectations as design context;
the fifteen-image gate was not achieved. Reference hashes, strict checker behavior, golden
tolerances and failed-run evidence remain unchanged. The
[milestone record](../milestones/m6.5.md) preserves the baseline/current reproduction and limits;
the [roadmap](../roadmap.md#m65--display-boundary-and-edr-evaluation) owns the accepted exception
and separate follow-up work. This is not approval to alter rendering or silently update goldens.

EDR closes as DEFER under [ADR 0019](../decisions/0019-display-domains-and-edr.md). The owner
confirmed matching UI-white brightness, but the proposed peak-scaled Neutral curve changed
midtones and full presentation fallback/production cost remain unvalidated. No EDR source ships.

## 1. Purpose

Since M5 the frame has had exactly one place that leaves scene-linear space: the display
transform (`Shaders/DisplayTransform.slang`, ADR 0006) tone maps with Khronos PBR Neutral and
encodes sRGB into a Renderer-owned 8-bit target. Everything that follows treats that target as
"the picture" without saying what it is: the swapchain is an untagged `BGRA8Unorm` drawable, the
editor UI composites over the encoded image in encoded space, screenshots are metadata-free BMPs,
and the only colour statement in the whole system is a manifest string literal, `"sRGB LDR"`,
that the comparison tool checks by equality. The RHI's validation layer refuses float swapchain
formats with an "SDR" message precisely because no presentation mode beyond that one has ever
been established.

M6.5 turns those facts into contracts. The output domain becomes a named, serialised
`DisplayDomain`; the UI composite is declared (encoded space, straight alpha, SDR white, backing
density) and its density and 1:1 viewport mapping are verified; captures can carry their domain in
the file itself; a fixture renders known ramps and colours through the real display pass into
in-repo goldens; and a throwaway probe on an experiment branch measures what the development
machine's XDR display and the platform actually offer for extended dynamic range, so ADR 0019 can
record adopt or defer with evidence and a reference-white/headroom policy any future adoption must
honour.

## 2. Adopted boundary and reference model

- **The picture does not change.** `Shaders/DisplayTransform.slang`, `Tonemap.slang` and
  `Encode.slang` are untouched. Every M6.4 parity and vendor screenshot hash, every golden dump,
  every oracle tolerance and every `[checkpoint-a]` case stays as it is. M6.5 adds description,
  verification and metadata around the transform, not a new transform.
- **One domain, named once.** `Source/Render/DisplayDomain.h` is the single owner of what the
  display target encodes. The Renderer exposes it, the manifest and PNG metadata serialise it, the
  Inspector shows it, the tests assert against it. No second copy of the facts lives in App or
  Tools.
- **The UI composites in encoded space at SDR white.** Dear ImGui draws display-referred,
  sRGB-encoded colours with straight alpha into the `BGRA8Unorm` drawable over the already
  encoded scene image, exactly as it does today. This is declared, not changed: it is the domain
  ImGui's style colours are authored in, and any linear-light alternative would visibly re-weight
  the editor for no portfolio gain. UI content never exceeds encoded 1.0 — the SDR white policy an
  EDR adoption would have to keep.
- **The RHI does not grow on `main`.** No presentation-domain field, no headroom query, no float
  swapchain format is accepted. The engineering convention requires a current caller and two
  credible implementations before an interface exists; the SDR path has one implementation and
  the EDR path has, until ADR 0019 says otherwise, none. The validation refusal and its test stay.
- **EDR is evaluated, not adopted.** All extended-range code — float drawable, colorspace,
  headroom reads, a linear-output transform variant, a linear UI composite — lives on
  `exp/m6.5-edr` and is measured on the built-in Liquid Retina XDR display. Only conclusions, the
  ADR and its policy return to `main`. If the ADR says adopt, the adoption is its own later slice,
  as the roadmap already provides.
- **Additive everywhere else.** One Render header, one Engine image writer, one App metadata
  path and format switch, one Inspector block, one GPU fixture with goldens, one Tools parity
  script, one ADR. Existing command lines keep working unchanged; `.bmp` outputs stay
  byte-identical.

## 3. The display domain (`Source/Render/DisplayDomain.h`)

A plain header below Engine in the dependency chain, so Render, Engine, App and Tests can all
name the same facts:

```cpp
namespace lmx::render {

enum class DisplayView : uint8_t { Sdr };                 ///< Which output view a frame produced.
enum class TransferFunction : uint8_t { Srgb };           ///< IEC 61966-2-1 piecewise encode.
enum class ColorPrimaries : uint8_t { Bt709 };            ///< sRGB / Rec. 709 primaries, D65.
enum class ToneMap : uint8_t { PbrNeutral };              ///< Khronos PBR Neutral (Tonemap.slang).

/// What the display target holds after `lmx.pass.display`. Encoded 1.0 is the display's SDR
/// reference white; `peakWhite` is the tone map's peak relative to it (1.0: the SDR transform
/// rolls everything above reference white into range). The target is opaque: alpha is 1.0 and
/// carries no coverage.
struct DisplayDomain {
    DisplayView view = DisplayView::Sdr;
    TransferFunction transfer = TransferFunction::Srgb;
    ColorPrimaries primaries = ColorPrimaries::Bt709;
    ToneMap toneMap = ToneMap::PbrNeutral;
    float referenceWhite = 1.0f;
    float peakWhite = 1.0f;
    uint8_t bitsPerChannel = 8;
    bool opaque = true;
};

inline constexpr DisplayDomain kSdrDisplayDomain{};

std::string_view name(DisplayView);        // "sdr"
std::string_view name(TransferFunction);   // "srgb"
std::string_view name(ColorPrimaries);     // "bt709"
std::string_view name(ToneMap);            // "pbr-neutral"
std::string describe(const DisplayDomain&); // one human line for logs and the Inspector
std::string toJson(const DisplayDomain&);   // the manifest's and PNG's `display` object

} // namespace lmx::render
```

`Renderer::displayDomain()` returns `kSdrDisplayDomain`; `kDisplayFormat` (`BGRA8Unorm`) is
documented as the storage of that domain and a `static_assert` ties `bitsPerChannel` to it. The
single-valued enums are deliberate: they are the vocabulary the probe extends on its branch
(`DisplayView::Edr`, a linear transfer, a peak above 1.0) and the vocabulary the manifest and the
comparison tool validate, so that an image or a run can say what it is without a string literal.

The JSON shape, `schemaVersion` 2 of the sequence manifest and the PNG text chunk alike:

```json
"display": {"view": "sdr", "transfer": "srgb", "primaries": "bt709", "toneMap": "pbr-neutral",
            "referenceWhite": 1.0, "peakWhite": 1.0, "bitsPerChannel": 8, "opaque": true}
```

## 4. The UI composition domain (`Source/App`)

Declared rule, recorded next to `kUiClearColor` in `Source/App/main.cpp` and in ADR 0019:

- The UI pass (`lmx.pass.ui`) targets the swapchain drawable, `BGRA8Unorm`, cleared to a
  display-referred, sRGB-encoded colour written verbatim. ImGui's vertex colours and font atlas
  are display-referred sRGB; the Metal 4 backend applies no transfer function and blends with
  straight alpha in encoded space. Layout is in platform points; rasterisation is at the
  viewport's framebuffer scale, which the vendored 1.93 backends supply per window
  (`Platform_GetWindowFramebufferScale`, dynamic font textures). UI brightness is bounded by
  encoded 1.0, the SDR reference white.
- The Viewport panel shows `Renderer::colorTarget()` through `ImGui::Image` at panel points ×
  framebuffer scale, so once the debounced resize settles the display target maps 1:1 onto
  backing pixels with the linear sampler at identity. During the debounce the previous image is
  stretched; this stays accepted and documented.
- Detached platform windows (the Render Graph window) are separate `CAMetalLayer`s the ImGui
  backend owns, always `BGRA8Unorm`, and therefore always SDR. They are outside the RHI swapchain
  and outside any EDR decision.

Verification, not modification: the expected state on the development machine is that Retina
text is already rasterised at 2× density. Track C confirms it (Section 9) before anything is
changed, and only a measured shortfall — a font baked at 1× on a 2× viewport, or a viewport
image resampled away from 1:1 — turns into code. The Inspector's Rendering subject gains a
read-only **Display** block: the domain's `describe()` line, the UI rule in one line, the main
viewport's framebuffer scale, the display target extent and whether the viewport image is
currently 1:1.

## 5. Capture encoding and metadata

### 5.1 PNG writer and reader (`Source/Engine/PngImage.h`)

Engine already owns image decoding (stb, cgltf) and offline baking, and it is the layer with the
`stb` package, so the writer lives there:

```cpp
namespace lmx::engine {

struct PngTextChunk { std::string keyword; std::string text; }; ///< Latin-1 `tEXt` entry.

/// 8-bit RGBA, non-premultiplied, top-down rows. Chunks in order: IHDR, sRGB (perceptual),
/// gAMA (45455), cHRM (sRGB/D65), one tEXt per entry, IDAT, IEND. Deterministic: no timestamp.
std::expected<void, AssetError> writePng(const std::filesystem::path&,
                                         std::span<const uint8_t> rgba, uint32_t width,
                                         uint32_t height,
                                         std::span<const PngTextChunk> text = {});

struct PngImage { uint32_t width, height; std::vector<uint8_t> rgba;
                  std::vector<PngTextChunk> text; };
std::expected<PngImage, AssetError> readPng(const std::filesystem::path&);

} // namespace lmx::engine
```

`stb_image_write` produces the signature, IHDR and the compressed IDAT/IEND; the writer inserts
the colour and text chunks between IHDR and the first IDAT with its own CRC-32, since stb writes
none of them. `stb_image` decodes; the reader also walks the chunk list for `tEXt`, which stb
discards. Both are CPU-only and unit tested (Section 9). `BGRA8Unorm` readbacks are swizzled to
RGBA before writing; nothing else about the bytes changes.

### 5.2 Screenshots and sequences (`Source/App/Screenshot.cpp`, `AppOptions`)

- `--screenshot <path>` chooses the container by extension: `.bmp` writes the existing header
  and bytes unchanged; `.png` writes through `writePng` with two text chunks, `lmx:display`
  holding `toJson(displayDomain)` and `lmx:frame` holding the run's scene, frame count, temporal
  mode, effective mode and fallback, render scale, debug view and device name. Any other extension
  is a parse error naming both accepted ones.
- `--capture-sequence` gains `--capture-format png|bmp`, default `png`; frame files are
  `frame-%06d.png` or `.bmp` accordingly and every PNG carries the same two chunks.
- The manifest moves to `schemaVersion` 2: the `colorSpace` literal is replaced by the `display`
  object of Section 3 plus `"container": "png"|"bmp"`, and a new `ui` object records that the
  offscreen path composites no UI (`{"composited": false}`), so a future windowed capture can say
  the opposite. Every other field keeps its name, type and precision.
- `Tools/TemporalCompare/compare.py` accepts version 1 (`colorSpace == "sRGB LDR"`) and version 2
  (`display.view == "sdr"` and `display.transfer == "srgb"`; anything else is refused with the
  offending values named), loads frames by the manifest's `file` field whatever the container, and
  `test_compare.py` covers both versions. The guide's recorded commands keep working.

## 6. SDR fixtures and goldens

A GPU test file, `Tests/GpuDisplayTests.cpp`, renders synthetic scene-linear content through the
real `Shaders/DisplayTransform` pipeline — the same library, the same `BGRA8Unorm` target, the
same bloom-off 1×1 fallback — and pins the bytes:

- **Ramps fixture, 256×64, `Tests/Golden/display-sdr-ramps.png`.** Eight 8-pixel rows: linear
  0→1 in 256 steps; linear 0→4 (the roll-off above reference white); a grey ramp in stops from
  −8 to +4 EV around 0.18; per-channel red, green and blue 0→2; the six MaterialLab known colours
  as flat patches; and a hue sweep at luminance 1.5 to exercise PBR Neutral's desaturation. The
  scene texture is filled from the CPU as exact binary16 values so the fixture has no shading
  dependency.
- **Composite fixture, 64×64, `Tests/Golden/display-sdr-bloom.png`.** The ramps' first row
  plus a CPU-filled half-resolution bloom texture composited at intensity 0.2, pinning the
  bilinear reconstruction path the M6.2 test checks against the oracle.

Each golden is compared per channel: the test fails on any channel further than 1/255 from the
golden and reports the count and the maximum, and the milestone records the SHA-256 of a
byte-identical run on the reference device. The 1/255 allowance covers a different Apple GPU's
`pow`, not a transform change — a 2/255 drift anywhere fails. The same test asserts the fixture
against the existing CPU oracle (`Tests/DisplayTransformOracle.h`) within 1/255, so the golden
pins the bytes and the oracle explains them. On mismatch the actual image is written beside the
golden, following `GraphDumpTests`' convention, and `LMX_UPDATE_GOLDENS=1` rewrites it
deliberately. A CPU unit test decodes each golden and checks its `lmx:display` chunk against
`kSdrDisplayDomain`, so a golden cannot silently belong to another domain.

**Scene reference images** stay out of the tree. `Tools/Screenshots/parity.py` re-renders the
fifteen M6.4 screenshots (nine native, six vendor; 1280×720, fixed camera, `--frames 32`, `.bmp`)
and compares their SHA-256 against `Tools/Screenshots/reference.json`, which records each hash,
the device, macOS, Xcode and build mode they were taken with. It exits non-zero on any mismatch,
prints a per-image table, and supports `--selftest`. The M6.4 milestone's hashes seed the table.

## 7. The EDR probe (`exp/m6.5-edr`) and ADR 0019

### 7.1 What the probe builds (throwaway)

A branch-only `--edr` flag on the windowed App that, on the development machine:

- Sets the SDL-owned `CAMetalLayer` to `RGBA16Float`, colorspace extended linear sRGB and
  `wantsExtendedDynamicRangeContent`, through metal-cpp's `setColorspace` and a selector send for
  the flag (the vendored `CAMetalLayer.hpp` binds `colorspace` but not the EDR flag). The RHI
  validation refusal is bypassed on the branch only.
- Reads `SDL_PROP_WINDOW_HDR_ENABLED_BOOLEAN`, `SDL_PROP_WINDOW_SDR_WHITE_LEVEL_FLOAT` and
  `SDL_PROP_WINDOW_HDR_HEADROOM_FLOAT` every frame and on `SDL_EVENT_WINDOW_HDR_STATE_CHANGED`
  (SDL 3.4.12), and cross-checks them once against `NSScreen`'s
  `maximumExtendedDynamicRangeColorComponentValue` and its `maximumPotential…` and
  `maximumReference…` siblings from a small Objective-C++ file.
- Adds a display-transform variant that outputs linear light with the tone map's peak at
  `min(headroom, cap)`: input divided by the peak, PBR Neutral, output multiplied by the peak.
  Below the compression start this is the identity, so mid-tones are exactly the SDR transform's.
  The scene target, exposure and temporal passes are untouched.
- Composites the UI into the linear float drawable with ImGui's colours decoded to linear and
  clamped to 1.0, so the UI sits at SDR white while the scene may exceed it.
- Renders a calibration frame: flat patches at 0.25, 0.5, 1.0, 2.0, 4.0 and the current
  headroom, the ramps fixture, and the editor UI, alongside the SDR path in a second window.

### 7.2 What the probe measures

| Measurement | Method | Records |
|---|---|---|
| Reported headroom and SDR white | SDL properties and `NSScreen` at three brightness levels in the display's default and reference presets | values, agreement, change latency |
| Visible dynamic range | calibration patches on the XDR display, viewed and photographed beside the SDR window | which patches are distinguishable; peak reached |
| UI white policy | UI panel over a patch at 1.0 and at headroom | UI white matches SDR white; no boost |
| Cost | `lmx.pass.display` and `lmx.pass.ui` GPU times and drawable memory, SDR vs EDR, ten samples each | raw timings, no speedup claim |
| Robustness | window moved between displays, brightness change, headroom dropping to 1.0, `MTL_DEBUG_LAYER=1` | validation-clean; graceful fallback |
| Capture | `screencapture` of the EDR window and a float readback of the linear image | what a capture can and cannot preserve |

### 7.3 The decision (ADR 0019)

ADR 0019, *Display domains and the EDR decision*, records the SDR display domain, the UI rule,
the capture metadata contract and one of:

- **Adopt** — only if the probe shows a visibly better image on the XDR display at acceptable
  cost, validation-clean, with UI at SDR white, a fallback to the SDR domain whenever headroom is
  1.0 or the layer refuses the configuration, and a capture that names its view. Adoption then
  becomes its own slice with its own RHI growth; M6.5 still ships no EDR code.
- **Defer** — with the specific evidence that fell short and what would reopen it.

In both outcomes the ADR fixes the policy: encoded 1.0 is the SDR reference white in every view;
the tone-map peak follows the current headroom, smoothed, never a fixed nit target; UI never
exceeds reference white; the scene, exposure and temporal contracts (ADRs 0013–0017) are read
only, never redefined, by a display view; detached windows stay SDR; and every capture identifies
its view. Raw probe evidence stays outside the source tree, beside M6.4's evidence bundles.

## 8. App, Inspector, command line

- `Renderer::displayDomain()` is logged once at startup with `describe()`, next to the existing
  swapchain line.
- The Inspector's Rendering subject gains the read-only Display block of Section 4 after the
  Temporal block; nothing in it is editable.
- `--screenshot` accepts `.png` and `.bmp`; `--capture-format` selects the sequence container;
  the help text and `AGENTS.md` name both.
- `EditorRenderSettings` and `SceneView` gain no field: the domain is not a setting.

## 12. Non-goals

Per the roadmap, M6.5 does not adopt EDR, add a display-referred tone-map choice, expose
reference white or peak as settings, or change any scene, exposure or temporal semantics. It also
does not switch the UI to linear-light compositing, add EXR or float captures, add an ICC profile
or PQ/HLG metadata, tag BMP files, change the screenshot extent, make the RHI swapchain accept a
float format, touch the detached platform windows, or require a second display.

## 13. Exit gate

The roadmap M6.5 gate applies: fixed SDR gradients and reference images pass; the UI has the
intended brightness and resolution; EDR adopt or defer is recorded with evidence and limits,
without changing scene, exposure or temporal semantics or requiring another display. In addition:
both goldens pass within 1/255 with a byte-identical hash recorded on the reference device; all
fifteen M6.4 screenshot hashes reproduce through `parity.py`; a `.png` screenshot decodes to the
same bytes as its `.bmp` twin and carries `lmx:display` equal to `kSdrDisplayDomain`; manifest v2
validates in `compare.py` and the M6.4 report commands still run; the Inspector reports
framebuffer scale and a 1:1 viewport on the development machine; ADR 0019 is Accepted with the
Section 7.3 policy; and `main` contains no extended-range presentation code.
