# M5.3 — Editor Workspace and Selection — Design Spec

**Date**: 2026-08-13
**Status**: Implemented
**Boundary authority**: `docs/roadmap.md` M5.3 owns the outcome, deliverables, exit gate, and
deferrals. This spec decomposes that boundary without expanding it; where wording differs, the
roadmap wins. M5.3 changes App-owned editor organization and interaction only. It does not change
render-graph compilation or execution, renderer image formation, Engine scene identity, or RHI
semantics.

## 1. Purpose

M5.3 turns the existing docked shell into a repeatable renderer workspace. Scene navigation,
selection, contextual property editing, rolling performance observation, and exact compiled-frame
debugging become separate tools rather than sections of one overloaded Inspector. The editor gains
clear state and lifetime contracts around layout migration, scene changes, hidden panels, viewport
input, and actions that the frame loop must execute at a safe boundary.

The milestone deliberately delivers professional usability and observability rather than another
rendering technique. The current PBR/HDR renderer, frame graph, timing publication, scene catalog,
and three-frames-in-flight behavior remain the baseline being operated and inspected.

## 2. Adopted boundary and reference model

- **App-owned workspace.** Panel visibility, dock topology, selection, filters, pause state, and
  action intents belong to `Source/App`. `Engine::Scene` remains the owner of editable scene data;
  Render remains a frame-local consumer through `SceneView`.
- **One selected subject.** The Scene panel selects at most one editor camera, rendering-settings
  context, directional light, or object. The Inspector edits only that subject.
- **No false hierarchy.** The current scene model is a flat object list plus one editor camera and
  three directional lights. The Scene panel groups those subjects for navigation but does not claim
  parent/child transforms, entity composition, attachment, or reparenting.
- **One source per setting.** Viewport shortcuts and the Rendering Inspector edit the same existing
  editor state. They do not create parallel exposure, bloom, shadow, wireframe, clear-color, or
  transient-pooling values.
- **Existing observability contracts survive.** Performance remains a rolling summary over retired
  frames; Render Graph remains the exact newest retired frame joined to its own timings. Neither is
  relabeled as the other or merged into an ambiguous current-frame view.
- **No renderer side effects.** Offscreen scene screenshots remain identical for fixed scene,
  camera, settings, hardware, and build. M5.3 declares no new pass, resource, shader, graph use, or
  synchronization requirement.

The information architecture follows the useful separation in the official
[Unreal Editor interface](https://dev.epicgames.com/documentation/en-us/unreal-engine/unreal-editor-interface),
[Outliner](https://dev.epicgames.com/documentation/en-us/unreal-engine/outliner-in-unreal-engine),
and selection-driven Details panel, while remaining bounded by Luminex's much smaller flat scene
model. Docking continues to use Dear ImGui's
[documented docking workflow](https://github.com/ocornut/imgui/wiki/Docking); its internal
DockBuilder dependency stays contained in the editor implementation rather than leaking into
testable workspace models.

## 3. Workspace model

The editor has five independently visible top-level panels:

| Panel | Responsibility | Default |
|---|---|---|
| `Scene` | Active-scene choice, filtering, grouped subjects, single selection | open, docked left |
| `Viewport` | Rendered image, camera input, compact rendering toolbar | open, docked center |
| `Inspector` | Properties of the selected subject only | open, docked right |
| `Performance` | Coherent rolling frame-interval and GPU-pass observations | open, docked below Viewport |
| `Render Graph` | Exact newest-retired compiled-frame record and dump | closed; opens in the lower dock |

Panel visibility is one app-owned value per panel. A Window-menu checkbox and the corresponding
window close button read and write the same value, so close, reopen, and reset cannot disagree.
Closing a panel does not destroy its logical state: reopening Scene retains its filter and valid
selection, reopening Performance retains its history unless Clear History was requested, and
reopening Render Graph resumes with the newest eligible retired frame.

The default dock topology allocates approximately 18% of the work area to Scene, 24% to Inspector,
and 25% of the central height to Performance, with the Viewport taking the remainder. The builder
clamps Scene to at least 220 points, Inspector to at least 320 points, and the Viewport content
region to at least 640×360 points; the menu bar's height is outside the work area these figures
describe. When a window cannot satisfy all minima, the Viewport wins and the side panels narrow
proportionally or require scrolling.
Render Graph opens into the Performance dock as a separate tab but remains independently closable
and floatable.

The main menu is submitted before the dockspace so the viewport work area excludes the menu bar.
The dockspace itself is submitted every frame even when individual panels are hidden, preserving
docked-window ownership and restoration.

## 4. Workspace persistence, migration, and reset

Dear ImGui continues to persist window and docking data in `imgui.ini` next to the built binary.
Luminex adds app-owned workspace metadata to that settings file: a schema version and the five panel
visibility values. The metadata is written through a registered ImGui settings handler as its own
section of the same file, so one save path owns both kinds of data and no sidecar settings file
appears. Dock placement remains Dear ImGui data; schema and visibility are Luminex data.

- A clean run with no workspace metadata builds the M5.3 default topology and default visibility.
- An M5.2 `imgui.ini` has no M5.3 workspace schema and is therefore a legacy layout. Its first M5.3
  run builds the new default once instead of restoring the old two-column layout with floating or
  missing panels, then records the current schema.
- A matching M5.3 schema restores the user's docking, sizes, active tabs, floating windows, and
  visibility without rebuilding the default layout.
- An older or otherwise unrecognized schema is treated as legacy. Migration never guesses how new
  panels fit into an obsolete topology.
- Reset Default Layout restores default visibility and rebuilds only the Luminex dock topology at
  the current work-area size and display scale. It does not delete the entire ini file or unrelated
  Dear ImGui settings.
- Reset is idempotent: repeated requests produce the same topology and do not accumulate nodes,
  floating copies, or stale dock assignments.

The schema version changes only when a persisted workspace contract or required default topology
changes, not for cosmetic spacing or labels. Tests use in-memory settings text or temporary files;
they do not depend on a developer's real `imgui.ini`.

## 5. Selection identity and lifetime

The normative selection shape is a value, not an owning or borrowed pointer:

```cpp
enum class EditorSubject {
    None,
    Camera,
    Rendering,
    DirectionalLight,
    Object,
};

struct EditorSelection {
    engine::SceneId sceneId;
    EditorSubject subject = EditorSubject::None;
    size_t index = 0;
};
```

`index` is meaningful only for `DirectionalLight` and `Object`. A resolver compares `sceneId` with
the active catalog scene and validates the index against the active scene on every use. It returns
an ImGui-free resolved kind/value or invalid result; UI drawing never caches a `SceneObject*` or
`DirectionalLight*` across scene changes or vector mutation.

Selection transitions are fixed:

- Startup selects `Camera`, the one subject every active scene provides.
- A successful scene switch updates the active scene, resets the editor camera to that scene's
  initial pose, clears the Scene filter, and selects the new scene's `Camera`.
- A failed scene switch retains the active scene, camera, filter, and selection exactly; it logs the
  existing recoverable error and does not briefly publish the requested scene identity.
- Selecting the already-active catalog scene changes nothing.
- A stale scene ID or out-of-range subject index resolves to `None` and stores that healed value
  before the Inspector draws.
- Filtering changes visibility only. If the selected object is filtered out, selection and the
  Inspector remain valid; clearing the filter reveals the same selected row.
- Duplicate display names do not share selection or widget state. Subject kind and index provide
  the stable editor-local row identity for the lifetime of the active scene.

This is not a durable scene identity. It is intentionally invalid across a successful scene switch,
is never serialized as authored content, and is never passed to Render or the RHI. M7 remains the
owner of stable GPU-scene instance and resource identities.

## 6. Scene panel

The Scene panel contains, in order:

1. The existing scene-catalog selector, including availability hints and failure behavior.
2. A case-insensitive text filter over subject display names.
3. `Workspace` rows for `Editor Camera` and `Rendering`.
4. A `Directional Lights` group with the three existing lights in index order.
5. An `Objects` group preserving `Scene::objects` order.

Grouping is presentational and deterministic. It does not alter scene ordering or introduce a tree
into Engine. Mouse selection and Up/Down keyboard navigation operate on the currently visible rows;
keyboard navigation starts at the first visible row when the retained selection is filtered out.
The filter never mutates scene data, and an empty result displays a clear no-matches state rather
than an empty unlabelled panel.

The scene selector moves out of Inspector because it changes the context the whole workspace
observes. Scene loading keeps the existing `device.waitIdle()` ownership rule: in-flight frames may
still reference the prior scene, so the UI request is applied through the established scene-switch
boundary rather than by replacing `m_activeScene` inside a property widget.

## 7. Context Inspector

Inspector begins with the selected subject's kind and display name and then draws only its relevant
properties. With `None`, it shows `Select an item in Scene` and no editable fallback sections.

- **Camera:** world-space position, yaw and pitch in degrees, vertical FOV in degrees, positive near
  and far clip distances with `near < far`, and fly speed in world units per second. Reset Camera
  restores the active scene's initial pose and Camera defaults. Clear color is not a camera field.
- **Rendering:** display-authored clear color decoded by the existing scene-linear boundary;
  wireframe; manual exposure; automatic-exposure enable and metering parameters; bloom enable,
  threshold, and intensity; shadow-filter choice; and transient pooling. Existing ranges, reset
  triggers, defaults, and scene-switch persistence remain unchanged.
- **Directional light:** index and role, world-space ray direction, and non-negative scene-linear RGB
  radiance. Values above one remain editable HDR values. Light 0 is labelled `Shadow caster`; lights
  1 and 2 are labelled `Unshadowed`. Direction edits reject a zero vector and store a normalized
  vector, preserving the renderer contract.
- **Object:** display name; editable world-space position, XYZ Euler rotation in degrees, and
  positive non-zero scale; read-only mesh and material indices. Material parameters, texture
  replacement, renaming, and authored reset history are not implied by these rows.

Fields use aligned tables and explicit space/unit labels where the value would otherwise be
ambiguous. UI clamping prevents invalid interactive values, while existing Engine and Render
assertions continue to protect programmer contracts. Inspector does not hold references beyond the
draw call that resolved them.

## 8. Viewport controls, input, and resize

The Viewport retains the scene image as its dominant content and adds one compact toolbar above it.
The toolbar shows the active scene and exposes Reset Camera plus quick controls for wireframe,
manual/automatic exposure mode, bloom, and PCF/PCSS shadow filtering. Detailed parameters remain in
the Rendering Inspector. Toolbar and Inspector controls edit the same state immediately; changing
one is visible in the other on the same UI frame.

Viewport target sizing uses only the image content region below the toolbar, converted from logical
points to backing pixels through the existing display scale. The current ten-stable-frame debounce,
device drain, target replacement, ImGui texture retirement, and exposure-reset rules remain. A
layout reset, panel toggle, or splitter drag may resize the target, but once the extent stabilizes it
produces one successful resize and one corresponding exposure reset rather than repeated churn.

Relative-mouse look remains gated by a right-button press over the Viewport. The editor must leave
relative mode, restore the cursor, clear its look latch, and discard accumulated relative motion
when any of these occurs:

- the right button is released;
- Viewport is closed or collapsed;
- the application window loses focus;
- Reset Default Layout begins; or
- editor shutdown starts.

Closing Inspector, Scene, Performance, or Render Graph does not interrupt camera input. M5.3 adds no
viewport picking, selection outline, focus-selected operation, or transform gizmo.

## 9. Menu and action boundary

The main menu contains only behavior the milestone actually supports:

| Menu | Actions |
|---|---|
| `File` | `Quit` |
| `Window` | Toggles for Scene, Viewport, Inspector, Performance, and Render Graph |
| `Layout` | `Reset Default Layout` |
| `Debug` | `Capture Next GPU Frame` with the existing `C` shortcut shown |

Menu drawing produces App-owned action intents. It does not quit SDL, wait on the device, resize a
target, or begin Metal capture directly. The frame loop consumes each intent at the boundary that
already owns the operation. Quit follows the normal window-close path. A capture intent joins the
existing keyboard/environment request and is consumed by the next frame that successfully acquires
a drawable; a skipped drawable does not lose it. A failed capture attempt is consumed and logged,
matching current behavior rather than retrying every frame.

The menu is a discoverable frontend to the existing programmatic Metal capture path described by
Apple's [capture workflow](https://developer.apple.com/documentation/xcode/capturing-a-metal-workload-programmatically).
It retains the `MTL_CAPTURE_ENABLED=1` requirement and existing absolute-path validation.

## 10. Performance panel

Performance moves the current Stats content out of Inspector and names every value by what is
actually measured:

- `Frame interval` and FPS come from App wall-clock delta. They are not labelled CPU render time.
- Viewport logical size and scene-target pixel extent are shown separately.
- The rolling GPU table has `Pass`, `Average`, `Latest`, `Min–Max`, and `Samples` columns in schedule
  order. The window remains 60 retired frames and the visible snapshot refreshes four times per
  second.
- A `Timed pass sum` may add the displayed pass measurements, but is explicitly not called total GPU
  frame time because present, driver, and untimestamped work are outside that sum.
- The newest displayed rolling frame ID, object/draw count, and transient requested bytes,
  high-water bytes, and alias savings identify the context around the timing rows. Transient values
  come from a retained compiled frame rather than a fresh unrelated graph.

Pause freezes one coherent display snapshot: frame ID, frame-interval plot, GPU rows, counts,
resolution, and transient-memory values stop together. Collection may either stop or continue
behind the frozen view, but resume publishes one internally consistent current snapshot; it never
mixes frozen pass rows with live memory or resolution. Clear History empties frame-interval and pass
history together and displays a waiting state until a new retired sample arrives.

As today, a changed ordered pass-label sequence resets every timing series rather than averaging
unlike schedules, and duplicate labels remain distinguished by schedule position. The presentation
model and pause/clear transitions are ImGui-free and unit-testable. M5.3 adds no CPU zones, present
timestamps, counters, trace export, sorting that destroys schedule order, or performance claim.

## 11. Render Graph preservation

Render Graph remains a separate top-level window over `GraphInspectorModel`. Opening, closing,
docking, floating, and resetting its placement do not change which frame it presents. It continues
to show the newest retained frame whose GPU timings have retired and joined by frame ID, including
resources, scheduled and culled passes, transitions, transient lifetimes and assignments, pooling
state, exact timings, and deterministic text dump.

The panel identifies its retired frame ID and whether no retired frame is available. Dump Frame
still serializes the displayed record, not the currently encoding frame. Performance pause does not
silently retarget Render Graph; each panel states its own time domain. M5.4 remains the owner of node
layout, dependencies as edges, selection inside the compiled graph, and alias visualization.

## 12. Testable editor models

Selection resolution, panel visibility, workspace-schema decisions, menu action intents,
Performance snapshot shaping, and pause/clear transitions are plain App models containing no SDL,
ImGui, Metal, or RHI backend types. Each model compiles into the existing Tests target, which links
no ImGui, SDL, or windowing dependency; a model that cannot join that target's source list without
new dependencies violates this section. Dear ImGui functions render those models and translate user
gestures into model transitions; they do not own hidden copies of the same state.

`EditorShell` may continue to coordinate the process-global ImGui context and scene interaction, but
the milestone extracts panel and model code enough that `EditorShell.cpp` is not the only place a
selection, migration, or performance rule can be understood or tested. This is a bounded
maintainability change, not a general editor framework or plugin architecture.

## 13. Testing and visual evidence

- CPU unit tests cover every subject kind, all three light indices, every object index, duplicate
  names, invalid-index healing, filtered selection, startup default, successful and failed scene
  switches, and repeated switching without stale selection.
- Workspace tests cover clean settings, representative M5.2 legacy settings, matching M5.3 custom
  settings, unknown schema, and repeated Reset Default Layout. Panel close buttons and Window-menu
  toggles share one visibility state.
- Action tests prove Quit and Capture emit intents only, duplicate capture gestures coalesce into one
  next-frame request, skipped drawables retain that request, and one failed attempt is consumed.
- Performance tests preserve the existing rolling-window, duplicate-label, schedule-change, and
  repeated-frame rules, then cover coherent pause, resume, clear, timed-pass sum, and retained-frame
  memory joins.
- Input tests or a focused harness cover right-button release, Viewport close, focus loss, reset, and
  shutdown leaving relative mode. Resize stress covers repeated panel toggles and layout resets
  without repeated stable-extent recreation.
- Visual QA covers clean, legacy, restored, and reset layouts at 1280×720, 1440×900, and 2560×1440,
  including Retina backing scale. The default Viewport is unobscured, long names do not overwrite
  fields, and every hidden panel can be recovered from the menu.
- Fixed-camera 1280×720 screenshots of Sponza, Damaged Helmet, and MaterialLab remain byte-identical
  to the M5.2 baseline on the same GPU and build settings. The editor runs under Metal validation;
  existing App, scene, renderer, exposure, bloom, frame-record, timing, and graph-inspector tests
  remain green.
- Formatting and `xmake policy` pass. The milestone record distinguishes automated evidence from
  manual visual checks and records any accepted deviation.

## 14. Delivery stages

The later active implementation plan may decompose these further but must preserve the selection,
time-domain, and no-renderer-change boundaries:

| # | Stage | Delivers |
|---|---|---|
| 1 | Pure workspace models | Selection resolver, panel visibility, schema decision, action intents, Performance snapshot and unit tests |
| 2 | Workspace shell | Main menu, versioned migration, deterministic default/reset topology, Scene/Viewport/Inspector/Performance extraction |
| 3 | Selection and properties | Searchable grouped Scene panel, contextual Inspector, shared Viewport shortcuts, scene-switch and input edge cases |
| 4 | Observability migration | Coherent Performance pause/clear/table, independently dockable exact-frame Render Graph, retained existing dump semantics |
| 5 | Evidence and record | Layout matrix, renderer screenshot parity, Metal validation, full tests, policy, current docs, milestone record |

## 15. Non-goals

Per the roadmap, M5.3 does not add viewport picking, selection rendering, outlines, object-ID passes,
transform gizmos, focus-selected bounds, multi-selection, scene hierarchy, parenting, an ECS,
persistent identities, rename or serialization, undo/redo, asset or content browsing, multiple
platform windows, new profiler instrumentation, trace export, Render Graph nodes or mutation, graph
execution or scheduling changes, renderer passes or shader changes, or RHI changes.

Also deferred are authored camera bookmarks or multi-preset systems, interactive image export,
MaterialLab-specific overlays, material editing, light-unit redesign, async scene loading, bloom or
shadow-filter changes, exposure adaptation, temporal reconstruction, GPU-scene work, and any attempt
to repair unrelated M5.2 capture-tool findings inside the editor milestone.

## 16. Exit gate

The roadmap's M5.3 exit gate applies verbatim: clean, M5.2 legacy, matching M5.3 restored, and reset
layouts keep a usable Viewport; every panel and menu action works; selection, filtering, successful
and failed scene changes, resize, and hidden-Viewport input preserve their contracts; Performance
pause presents one coherent rolling snapshot; Render Graph remains independently dockable and
frame-correct over the exact newest retired frame; fixed-camera renderer output is unchanged; and
the milestone adds no graph, renderer, scheduling, or RHI behavior.
